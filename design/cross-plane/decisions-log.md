## 一、已确认决策

### DEC-001：任务定义归属 — 控制面定义，协调面调度

**背景**：用户初始需求中将「采集任务管理」和「RC 任务管理」列在控制面，但以 `#` 标注了对其归属的疑问。核心矛盾是：控制面应该是「定义权威」，但任务的运行时调度是「区内实时行为」。

**候选方案**：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A：全在控制面 | TaskSpec 定义 + slot 分配 + 运行时调度全在中心 | 全局最优；简单 | 违反 P1（集中管理≠集中调度）；中心故障=全区停采 |
| B：全在协调面 | 各区自行定义任务，中心只审计 | 完全自治 | 丧失全局一致性；无法跨区协调 |
| **C：定义/调度分离** | 控制面定义 TaskSpec/RuleSpec；协调面生成 Manifest 并调度 | 符合 P1；降级自治；全局视图 | 需要 Manifest 下发协议 |

**最终选择**：方案 C。

**理由**：与核心原则 P1 完全一致。控制面是「做什么」的唯一权威，协调面是「怎么做」的区内权威。这也与 v0.2 取舍 2（任务内容与归属解耦）一致。

**影响模块**：C1-C8（控制面），K1-K2（协调面）

### DEC-002：采集器架构 — Job + Agent 分离 + OTel Collector 数据管道

**背景**：原始 v0.2 设计中 Collector 是全功能组件（调度+采集+数据输出）。经过多轮讨论，决定拆分为三个独立组件。

**候选方案**：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A：vmagent 单体 | 使用 Prometheus vmagent 作为采集器 | 生态兼容；简单 | 无法支持多类型 Agent；调度能力弱 |
| B：全功能 Collector | v0.2 原设计，Collector 承担所有职责 | 组件少；部署简单 | 职责耦合；扩缩不灵活 |
| **C：Job + Agent + OTel** | Job Scheduler 调度 + Agent 采集 + OTel Collector 数据管道 | 职责清晰；独立扩缩；OTel 生态 | 组件多；部署复杂 |

**最终选择**：方案 C。

**理由**：
- Job + Agent 分离使得调度逻辑和采集逻辑可以独立演进
- OTel Collector 作为统一数据管道，天然支持多输出路由、标签注入、缓冲重试
- OTel 生态丰富，后续扩展日志采集等能力无需重新设计

**影响模块**：D1（Job Scheduler），D2（Agent），D3（OTel Collector）

### DEC-003：时序存储 — VictoriaMetrics 全链路统一

**背景**：时序库选型影响整个技术栈。需要在 Prometheus TSDB 和 VictoriaMetrics 之间选择。

**候选方案**：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A：Prometheus TSDB | 原生 Prometheus 存储 | 生态标准 | 单点性能瓶颈；集群方案复杂 |
| **B：VictoriaMetrics** | 高性能时序数据库 | 单节点性能优异；集群模式成熟；兼容 PromQL；remote-write 兼容 | 社区相对小 |
| C：混合 | 中心用 VM，区内用 Prometheus | 各取所长 | 两套技术栈；运维复杂 |

**最终选择**：方案 B。

**理由**：
- VM 单节点性能远超 Prometheus TSDB，适合区内场景
- VM 集群模式（mode C）天然支持水平扩展
- 完全兼容 PromQL，Grafana 无需额外适配
- remote-write 协议兼容，OTel Collector 可直接输出
- 全链路统一降低运维复杂度

**影响模块**：D6（Storage），C8（Query Gateway），D5（Zone Query Proxy）

### DEC-004：RC 与存储绑定

**背景**：RC（RuleCheck）规则检测引擎应该部署在哪里？是全区部署还是按条件部署？

**候选方案**：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A：全区部署 | 所有网区都部署 RC | 告警覆盖完整 | Mode A 无本地数据可查；浪费资源 |
| **B：存储绑定** | RC 仅部署在有本地存储的网区（mode B/C） | RC 从本地存储取数，低延迟；不浪费 | Mode A 无规则告警 |
| C：中心集中 | RC 全部部署在中心 | 集中管理 | 中心负载大；跨区取数延迟高 |

**最终选择**：方案 B。

**理由**：
- RC 的核心行为是「从本地存储取数 → 评估规则 → 产生告警」
- Mode A 无本地存储，RC 无从取数
- 存储绑定使得 RC 的数据路径最短，不依赖跨区网络
- Mode A 的告警覆盖可通过中心「虚拟 RC」补充（见 DEC-004a）

**子决策 DEC-004a**：Mode A 告警补充方案
- [建议] 中心部署「虚拟 RC」，专门评估 mode A 网区的规则
- 虚拟 RC 从中心 VM 取数（mode A 数据通过 remote-write 到达中心）
- 阶段 1 可不做（接受 mode A 告警盲区），阶段 3 评估

**影响模块**：D4（RC），C4（Alert Management）

### DEC-005：任务路由 / 读取路由 / RC 路由 三路分离

**背景**：原始设计中任务下发和查询路由混在一起。实际上三者有不同的决策逻辑。

**三路分离定义**：

| 路由类型 | 决策内容 | 决策者 | 输入 |
|---------|---------|--------|------|
| 任务路由 | 实例的采集任务应该下发到哪个 zone | 中心控制面 | 实例所在网区（IP 段映射） |
| 读取路由 | 查询某实例数据时应该从哪里取 | 查询网关 | 该 zone 的存储模式 + 数据可用性 |
| RC 路由 | 规则检测应该在哪个 zone 执行 | 中心控制面 | 该 zone 的存储模式（跟随写入目的地） |

**理由**：
- 任务路由由实例的网段归属决定（相对固定）
- 读取路由由存储模式和数据可用性决定（可能动态切换）
- RC 路由由存储位置决定（跟随数据写入目的地）
- 三者独立使得每一路可以独立优化

**影响模块**：C1（Zone Management），C8（Query Gateway），K2（RC Task Scheduling）

### DEC-006：去除加权（当前阶段），采用均等分配

**背景**：v0.2 取舍 5 原本写的是「slot 必须按权重分配」，但后续讨论认为当前阶段应简化。

**候选方案**：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A：加权分配 | 按节点能力/资源分配不同数量的 slot | 资源利用率高 | 实现复杂；权重如何确定？ |
| **B：均等分配** | 所有节点平均分配 slot | 简单；可预测 | 异构节点利用不均 |
| C：均等 + 能力约束 | 均等分配，但只分配给有对应能力的节点 | 简单 + 基本合理 | 能力约束是轻量加权 |

**最终选择**：方案 B（阶段 1），后续迭代到方案 C，最终可能演进到方案 A。

**理由**：
- 当前阶段建议区内同构（新建区标准化部署），均等分配足够
- 异构场景（如节点 A 有 SNMP Agent，节点 B 没有）通过能力约束处理
- 后续正式引入加权时需回写 v0.2 取舍 5

**影响模块**：K1（Collection Task Scheduling），D1（Job Scheduler）

## 三、冲突记录

### CONFLICT-001：模式 A 与 v0.2 核心假设冲突

**描述**：v0.2 几乎所有设计都假设区内有本地 TSDB（Zone Query Proxy 聚合、WAL 回填、本地查询、数据连续性预算）。Mode A 无本地 TSDB，这些设计全部失效。

**影响**：
- Zone Query Proxy 在 mode A 不部署
- 连续性预算中 mode A 明确「中心不可达时数据全丢」
- remote-write 队列缓冲时长 = 可容忍最大空洞

**处理**：Mode A 定位为「非标准模式」，仅用于 1 节点区/边缘站点。

---

### CONFLICT-002：加权 vs 均等分配的历史遗留

**描述**：v0.2 取舍 5 明确写「slot 必须按权重分配」，v2 去除了加权改为均等。但 v3 又提出「异构 Agent 部署」场景，均等分配在此场景下失效。

**影响**：当前阶段均等分配 + 能力约束感知（本质是加权的轻量变种）。

**处理**：后续正式引入加权时需回写 v0.2 取舍 5。

---

### CONFLICT-003：v0.2 全区广播与凭据安全的矛盾

**描述**：v0.2 取舍 2 要求全区 Manifest 广播。但如果 Manifest 包含凭据（模型 1），凭据扩散到每个节点。

**处理**：Manifest 中不含凭据，只含 credential_id 引用。凭据通过独立通道按需获取。广播的是任务定义，凭据是执行时资源。

---

### CONFLICT-004：L3 自治与「中心为唯一权威」的张力

**描述**：v0.2 §3.2 规则 2 说「恢复时承认既成事实」，但 L3 期间 Job Scheduler 集群可能做出与中心期望态矛盾的归属决定。

**处理**：明确「既成事实」边界——归属决定承认，但与期望态矛盾时，中心恢复后触发「协商式再均衡」而非强制覆盖。详见 `degradation-autonomy.md`。

---

### CONFLICT-005：Mode A 告警覆盖缺失

**描述**：RC 与存储绑定后，mode A 网区无本地 RC，无法产生规则告警。

**处理**：
- 阶段 1：接受 mode A 告警盲区（mode A 定位为边缘/低优先级）
- 阶段 3：评估中心「虚拟 RC」方案

---

### CONFLICT-006：slot 总数恒定性 vs 业务增长

**描述**：slot 总数一旦定稿变更代价极高（全区重映射），但业务增长会导致 target 数量增加。

**处理**：
- 初始按预期最大规模 ×2 预留
- 引入「slot 拆分」机制（一个 slot 拆为两个，只影响该区）
- 显式接受「slot 总数变更 = 全区重映射」的高成本
