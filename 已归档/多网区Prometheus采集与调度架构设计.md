## 1. 设计目标与核心取舍

### 1.1 目标（按优先级）

1. **数据连续性最大化**：任何单点故障造成的样本空洞可量化、可压缩，计划内变更做到接近零空洞。
2. **采集不中断**：单节点、单协调器、单网区、跨区链路任一故障，都不应导致该区监控数据停摆。
3. **不双主、不脑裂**：同一 target 在同一逻辑时刻只有一个"被承认"的采集者；无法达成多数派时宁可空洞也不双主。
4. **集中管理、分散执行**：管理面单一权威，执行面区内闭环，两者通过版本化期望态解耦。
5. **变更可控**：迁移与轮动造成的时序断裂（churn）最小化。
6. **全链路可对账**：任意时刻、任意时点都能回答"哪个实例由哪个网区的哪个节点在采、生效哪个版本"。

### 1.2 七条必须先定下来的取舍

**取舍 1 · 集中管理 ≠ 集中调度**
中心是**唯一的定义权威**（任务定义、实例台账、网区映射、slot 总数、审计），但不是**实时裁决权威**。实时的"谁采什么、谁挂了、谁接管"必须在网区内闭环。
→ 理由：跨区链路是全系统最不可靠的一跳，而故障检测要求秒级响应。**用最弱的链路去决定最快的决策，是本架构最应该避免的错误。** 中心一旦进入实时检测回路，跨区抖动就会转化为全区监控抖动。

**取舍 2 · 任务"内容"与"归属"必须解耦（本轮最重要的设计变更）**
每个网区内的**所有** collector 都持有该区**完整任务清单**（全部 slot 的 target 定义），归属信息只是一份"我负责其中哪些 slot"的轻量映射。
→ 直接收益：接管时**无需任何外部拉取**，认领即采集，把接管时延从"检测 + 拉取配置 + 就绪检查"压缩到"检测 + 认领"。这是"最大限度保持数据连续"的关键前提，详见 §5.4 与 §13。
→ 代价：区内配置分发从"定向推给 owner"变成"全区广播"，存储冗余 ×N。但 zone 级 target 清单通常在 MB 量级（数万 target 也仅数 MB），代价可接受。

**取舍 3 · 检测权分布式化：peer 互探为主，中心为观察与仲裁方**
采用 VRRP 式节点间互相探测，检测在区内本地完成；节点同时上报"自身状态"与"我对同伴的探测结果"，中心得到一张 N×N 观测矩阵用于交叉验证、审计与仲裁，但**不作为接管的前置条件**。
→ 收益：接管时延不再包含跨区往返，SLO 可从 v0.1 的 60 s 收紧到 ~20 s。中心失联时区内照常自愈。

**取舍 4 · 一致性级别：at-least-once，允许短暂双采**
监控场景下"漏采导致告警漏报"的代价远高于"短暂双采产生重复样本"。接管允许 ≤1 个抓取周期的重叠窗口。
→ 配套约束：若各区 remote-write 到统一长期存储，**必须**为样本打 `collector_id` / `__replica__` 标签并在查询侧去重，否则双采会造成样本冲突与乱序。这条要在上线前定死标签规范。

**取舍 5 · 调度粒度：固定加权 slot，而非直接哈希到节点**
两级映射 `target → 固定 slot（数量恒定）→ collector（映射可变）`。节点增减只重映射少量 slot，避免大范围 target 迁移与 TSDB 序列断裂。slot 必须**按权重**（预估活跃序列数 / 抓取 QPS）分配——等权分片在真实环境必然出现"节点数一样但负载差数倍"。

**取舍 6 · 无多数派时选择"空洞"而非"双主"**
区内节点无法达成多数派共识时（如 2 节点区挂 1 台、或分区后少数派侧），**不进行接管**， slot 记入 `UNOWNED` 并触发最高级告警等待人工介入。
→ 这是必须显式接受的局限性，写进设计并演练，而不是留给线上暴露。§13.4 给出各场景的空洞预算。

**取舍 7 · 迁移有成本，所以要"懒"**
每次 slot 迁移都意味着该 target 时序在两个 TSDB 间分裂。再均衡必须带**迟滞 + 冷却 + 渐进**三重抑制（§14.2），宁可短期不均衡，也不要频繁迁移。故障恢复后**不物归原主**（§14.3）。

| 层 | 组件 | 职责 | 明确不做的事 |
|---|---|---|---|

| 管理面 | **观测矩阵汇聚** | 收集 N×N 探测结果，交叉验证、识别异常探测者、仲裁冲突归属 | 不发起秒级接管 |

| 协调面 | Zone Agent | 承载跨区通道（M1/M2/M3 任一）、快照同步、状态上报 | 不做调度决策 |

| 数据面 | Zone Query Proxy | 聚合区内多个 Prometheus 端点、时序拼接与去重 | 不做业务路由决策 |

## 3. 集中管理与分散执行的边界

### 3.1 权责切分

**中心集中管理（唯一权威，变更需审批+版本化）：**
- 实例台账、网段↔网区映射
- TaskSpec / RuleSpec 定义与 selector
- 每网区 slot 总数、权重计算规则
- 节点注册准入、版本门禁基线
- 运维意图标记（maintenance / quarantine / pin / cordon）
- 归属历史审计、对账基线、跨区查询路由

**网区分散执行（区内闭环，中心不可用时照常运行）：**
- 抓取执行与本地 TSDB 写入
- peer 互探、故障检测、存活判定
- slot 认领与接管（含 epoch 推进，见 §10.3）
- 计划内驱离的区内编排（Coordinator 不可用时由节点间协商）
- 告警规则评估与本地告警产生
- 有限度的负载再均衡（仅在 L1/L2，L3 冻结，见 §3.2）

### 3.2 四级降级自治阶梯（对应要求 12）

这是"主节点维护或网络不通时能自行管理"的具体落地形态。每一级都明确：**谁是权威、能做什么、冻结什么、如何恢复**。

| 级别 | 触发条件 | 权威归属 | 可用能力 | 冻结能力 |
|---|---|---|---|---|
| **L0 正常** | 中心 + 区 Coordinator + peer 互探 全可用 | 中心定义、Coordinator 登记、peer 交叉验证 | 全部 | — |
| **L1 中心不可达** | 跨区通道中断 / 中心控制面故障 | **区内 Coordinator** | 采集、peer 检测、接管、驱离、再均衡（基于 last-synced manifest） | 任务定义变更、台账变更、跨区路由变更 |
| **L2 Coordinator 主节点不可用/维护中** | 主节点故障或计划维护 | **Coordinator 备节点**（本地共识/RDS 租约选出） | 同 L1 | 同 L1；切换期 <`T_coord_failover` 内暂停迁移类动作 |
| **L3 协调器完全不可用** | 主备皆失（含双节点同时维护） | **Collector 集群自身（纯分布式 VRRP 自治）** | 采集、peer 检测、**按多数派共识接管**、优雅驱离协商 | 再均衡（冻结现有归属）、一切配置变更、slot 总数变更 |

**L3 是本设计对要求 12 的最强回应**：即使区内没有任何协调组件，只要区内多数派节点存活，采集与故障接管照常运转。实现依赖三件事——① 每节点持有全区任务清单（取舍 2）；② 每节点持有本地快照（§7）；③ peer 互探 + 多数派共识 + 确定性优先级认领（§9、§10）。

**降级与恢复的三条硬规则：**

1. **降级要显式且可观测**：每次进入 L1/L2/L3 都必须产生事件与告警，并在所有相关节点上打点 `degradation_level`。静默降级是最危险的状态——运维以为中心还在管，实际已经自治了很久。
2. **恢复时承认既成事实，不做全量覆盖**：中心/Coordinator 恢复后，先收集各区当前归属与 epoch，**接受**自治期间做出的归属决定，只登记 + 事后按需再均衡。绝不用"中心记录的旧归属"强行覆盖，否则会引发大规模无谓迁移和双主。
3. **冲突才仲裁**：仅当出现真实冲突（同一 slot 被两个节点以不同 epoch 认领，或自治期间归属与中心期望态语义矛盾）时，中心介入仲裁 → 判定保留方 → 另一方走**优雅驱离**（make-before-break）而非硬切，把仲裁本身的数据空洞压到接近 0。

## 4. 元数据与路由模型

三张核心映射构成平台"关联骨架"，全部由中心维护、带 revision、下发到消费方本地缓存。

### 4.1 实例台账（Instance Registry）

```
instance_id → { zone_id, ip, net_segment, labels{env,app,owner,...},
                agent_type, port, scrape_profile, status, last_seen }
```
- `zone_id` 是唯一权威归属，采集/规则/查询路由全部由它派生。
- 台账变更走审批 + 版本化，因为它是所有下发行为的输入。

### 4.2 网段 ↔ 网区映射（Segment Map）

```
net_segment(CIDR) → zone_id → { collector_endpoints[], rc_endpoints[],
                                query_proxy_endpoint, tsdb_endpoints[] }
```
- 支持最长前缀匹配以处理网段嵌套。
- **必须显式处理未匹配网段**：落入 `UNKNOWN` 桶 → 不下发 + 告警人工确认。**绝不能默认路由到某个区**，否则会造成静默错采且极难发现。

### 4.3 查询路由表

```
instance_id | net_segment | label_selector → zone_id → 数据源端点集合
```
- 查询网关本地缓存 + 订阅/自检更新（§6、§8），不轮询 DB。
- 与 slot 归属解耦：路由表回答"数据在哪个区"，slot 归属回答"区内谁在采"。

### 4.4 selector 与展开

```
selector ::= by_segment(CIDR...) | by_label(k=v...) | by_instance(id...) | union(...)
TaskSpec ::= { task_id, selector, scrape_profile, interval, timeout,
               metrics_relabel, scrape_offset_policy, zone_scope(derived), revision }
RuleSpec ::= { rule_id, group_name, selector, expr_list[], severity,
               zone_scope(derived), revision }
```

`scrape_offset_policy` 是本轮新增字段，用于数据连续性（§13.2）：**抓取相位必须由 target 自身属性确定性推导，而不是由各节点随机生成**，这样任何节点接手同一 target 时相位一致，样本时间轴可无缝续接。

控制面在下发前完成 `selector → 实例列表 → zone 分组 → Zone Manifest`。**展开结果必须快照留档**（含展开时刻的台账 revision），否则事后无法解释"当时为什么采了这批机器"。

## 5. 任务分发模型

### 5.1 四级模型（v0.2 调整）

```
TaskSpec (逻辑任务, 中心定义)
    │ selector 展开（依赖台账 revision）
    ▼
Zone Manifest (每网区一份完整任务清单)      ★ 全区广播，所有 collector 都持有
    │ 加权切分（slot 数恒定）
    ▼
WeightedSlot (调度与接管的最小单位)
    │ 归属映射（可变，轻量）                ★ 只有这一层是"分配"，且可区内自治决定
    ▼
Collector (区内执行者)
```

与 v0.1 的关键差异：**Zone Manifest 是全区广播的公共知识，归属映射才是被分配的对象**。这把"配置分发"（低频、可容忍延迟）与"归属裁决"（高频、要求秒级）彻底分离，是 L3 自治和快速接管的基础。

### 5.2 Zone Manifest 结构

```
ZoneManifest {
  zone_id, manifest_revision, content_hash,
  slot_count,
  slots: [ { slot_id, weight, offset_seed,
             targets: [ { instance_id, addr, port, profile,
                          interval, timeout, labels, scrape_offset } ] } ],
  generated_at, registry_revision
}
```

- `content_hash`：用于自检短路（§6.3 M2）与 peer 摘要比对（§9.3），避免全量传输。
- `offset_seed`：相位对齐种子，确保跨节点接管时抓取时刻一致（§13.2）。
- Manifest 必须**原子生效**：不允许"部分 slot 用新 revision、部分用旧 revision"，否则接管方与被接管方对同一 target 的定义不一致，会产生难查的数据错乱。

### 5.3 slot 数量建议初值

| 参数 | 建议初值 | 理由 |
|---|---|---|
| 每网区 slot 数 | `max(64, 当前 collector 数 × 16)`，上限 512 | 粒度够细才能均衡；过多则元数据与心跳开销上升 |
| 扩容余量 | 按预期最大 collector 数 × 16 预留 | slot 数变更是高成本操作（全量重映射 + 时序断裂），一次给够 |
| 单 collector slot 上限 | 由容量探测得出（CPU/内存/磁盘 IO/序列数） | 超限即停止分配并触发扩容告警 |
| 单 slot target 上限 | ≤ 200 | 超过则接管时冲击过大、迁移粒度太粗 |

> ⚠️ slot 总数一旦定稿，变更代价极高，务必在上线前用真实 target 规模与序列基数压测确定。

### 5.4 归属映射的载荷

归属信息刻意做得**极轻**，因为它要在 peer 互探中随每次广告交换（§9.3）：

```
Ownership { zone_id, slot_id, epoch, owner_id, owner_state,
            manifest_revision, claimed_at, handoff_from_epoch }
```

注意归属载荷里**不含 target 列表**——target 内容由 Manifest 提供，owner 只需知道自己持有哪个 slot。这正是取舍 2 的落地：归属变更不需要传输任务内容，所以可以走高频通道；任务内容变更不需要改动归属，所以可以走低频通道。

## 6. 集中管理与跨区连通模型（对应要求 7、11）

### 6.1 三种连通模型

用户已明确"必要时可开放 ZK/etcd 给其他网区，或通过接口让网区自检"，两者对应下面的 M1 与 M2。**关键结论先说：无论选哪个，实时故障检测与归属裁决都必须在区内闭环，跨区通道只承载低频期望态与状态摘要。**

| 模型 | 形态 | 优点 | 风险/代价 | 适用 |
|---|---|---|---|---|
| **M1 开放跨区 ZK/etcd** | 各区 Coordinator/Agent 直接 watch 中心侧共识集群的期望态节点 | 变更近实时；watch 语义天然；对账简单（revision 直接可比） | ① 需开放跨区端口，安全评审成本高；② 跨区链路抖动会传导为配置同步延迟；③ 若把共识集群本身跨区部署（多数派跨区），故障域全局化——**强烈不建议** | 网区间已有可靠专线、延迟低且稳定、区数少 |
| **M2 接口自检（推荐基线）** | 各区周期性向中心接口核对"我这个区应该有哪些任务"：先比 digest，不一致再拉增量 | 只需 HTTP/gRPC 单向出向；防火墙友好；实现简单；天然满足"网区自己去核对" | ① 有轮询开销（用 digest 短路后极小）；② 配置生效延迟 = 核对周期；③ 需自己实现增量与幂等 | 通用场景，尤其是跨区只允许接口访问时 |
| **M3 出向长连接 push** | 区内 Agent 主动建立出向长连接，中心推送变更 | 生效延迟最低；无入向开口；带宽利用最好 | 需维护连接保活、重连、消息幂等与补推 | 有实时下发需求且允许长连接 |

**推荐组合：M2 作为基线 + M3 作为加速（混合）**
- M3 长连接在线时走 push，配置秒级生效；
- 长连接断开时自动退化为 M2 定时自检，**不需要人工切换**；
- M2 同时作为常态兜底对账（即使 push 正常也低频跑一次 digest 核对），修复漏推/乱序/静默漂移。

若你们已有跨区 ZK/etcd 且运维成熟，可用 M1 替换 M3 承担 push 角色，但 M2 的自检兜底仍建议保留——它是最不依赖基础设施的一条路径。

### 6.2 M1 的两条红线

如果选择开放跨区 ZK/etcd，这两点必须守住：

1. **共识集群不得跨网区部署多数派**。ZK/etcd 的正确性依赖 quorum 低延迟互通；把多数派节点分散到不同网区，等于让任一区的网络抖动导致**全局**协调不可用。正确形态是：集群部署在中心侧（或某个可靠的核心区），其他网区作为**只读客户端**跨区 watch。
2. **不得让区内实时决策依赖跨区 watch**。Collector 的接管决策路径上不允许出现"等 ZK 通知"。跨区 watch 只用于同步 Manifest 与登记归属审计。

> 补充判断：M1 相比 M3 的净收益其实有限（两者都能做到近实时下发），但安全评审成本明显更高。除非团队已有成熟的跨区 ZK 运维体系，否则 M2+M3 是性价比更高的选择。

### 6.3 M2 接口自检的协议要点

```
① 各区 Agent 每 T_check（建议 30~60 s）请求：
     GET /zone/{zone_id}/manifest/digest
   ← { manifest_revision, content_hash, slot_count, generated_at }

② 本地比对 content_hash：
   一致 → 结束（99% 的情况，开销 ≈ 一次轻量请求）
   不一致 → 进入 ③

③ 拉取增量：
     GET /zone/{zone_id}/manifest/delta?from={local_revision}
   ← 增量（新增/修改/删除的 slot 与 target）
   若 delta 不可用（本地 revision 过旧）→ 拉全量快照

④ 原子应用 → 更新本地快照 → 回 ACK(revision)
   中心记录"该区已生效到 revision X"，用于对账与灰度可观测
```

**四条实现约束：**
- **digest 短路是必需的**，否则自检退化为高频全量拉取，等于换了个地方轮询 DB。
- **delta 必须可幂等重放**，以 revision 判重；网络重试不能造成配置重复应用。
- **拉取要有本地缓存兜底**：中心不可达时继续用 last-known-good，并打点"配置陈旧度"（§7.4）。
- **Collector/RC 不直连中心接口**，只与区内 Agent/Coordinator 交互。中心接口只被每区一个 Agent 调用，避免节点数增长把中心打爆（这是要求 6"不从数据库直接拉取"的延伸：**也不从中心接口直接高频拉取**）。

### 6.4 存储选型

| 方案 | 推送/订阅 | 租约与存活 | 跨网区适配 | 运维成本 | 定位 |
|---|---|---|---|---|---|
| **RDS (MySQL/PG)** | ❌ 无原生 watch | 需自建租约表 + 时钟约定 | ✅ 可跨区访问 | 低（多数团队已有） | **中心真源首选**；不做实时协调 |
| **etcd** | ✅ watch + lease，最贴合 | 原生 lease | ⚠️ 多数派必须同区 | 中 | **区内协调首选**（Coordinator HA、归属登记） |
| **ZooKeeper** | ✅ watch，强 | 临时节点天然支持 | ⚠️ 同上 | 中高（JVM、ensemble 调优） | 已有 ZK 体系时可作区内协调或 M1 载体 |
| **MQ（Kafka/RocketMQ/NATS）** | ✅ 推送强 | ❌ 无 | ⚠️ 需跨区通道 | 中 | 事件通道补充；Kafka 需 compacted topic 才能表达"状态"而非"事件流" |
| **自研 Coordinator（内存态 + RDS 快照 + 长连接）** | ✅ 自定义 | 需自实现租约 + fencing | ✅ 完全适配隔离 | 中（研发换运维） | 网区数量多时的务实选择 |

**按规模分档推荐：**

- **档位 A（网区 ≤ 5、单区规模大）**：中心 RDS + 每区 etcd 3 节点 + M2/M3 跨区通道。etcd 的 lease/watch/revision 与"心跳续约 + 变更推送 + 版本对账"几乎一一对应，自研量最小。
- **档位 B（网区 > 10 或单区规模小）**：中心 RDS + 每区自研 Coordinator 双节点（active/standby，RDS 租约行做选举与 fencing）+ M2 自检为主。给每个小区塞 3 节点共识集群的运维负担不现实。

**统一约束**：Collector/RC 一律不直连 RDS；所有分配相关表必须带 `revision`（单调递增）与 `epoch`（归属令牌）。

### 6.5 用 RDS 做租约的两个陷阱（档位 B 必读）

1. **不要用各节点本地墙钟判定租约过期**。时钟偏移会导致提前抢占或延迟接管。判定应基于权威方单一时间源 + 强制全网 NTP，且最终以 `epoch` 令牌而非时间戳裁决。
2. **必须有 fencing token**。仅靠"租约过期"不足以防脑裂（§10.3）。所有写操作携带 epoch，下游拒绝旧 epoch。

## 7. 本地快照体系与自管理（对应要求 12）

### 7.1 三类快照，各自解决不同问题

"要有一份本地快照"这句话在实现上必须拆成三类，因为它们的内容、更新频率、恢复用途都不同。**只做其中一类会导致特定场景下无法自愈**——这是最容易踩的坑。

| 类型 | 持有者 | 内容 | 更新时机 | 恢复什么 |
|---|---|---|---|---|
| **A. 任务清单快照**<br>（Zone Manifest） | 区内**每个** Collector / RC | 全区完整任务清单 + revision + content_hash | Manifest 变更时（低频） | 节点重启后**立即知道该采什么**，无需等中心；L3 自治的物质基础 |
| **B. 归属视图快照** | 区内每个节点 | 全区 `slot → owner → epoch` 映射 + 本地 digest | 每次归属变更（中频） | 节点重启后知道**当前谁在采什么**；接管时无需询问任何人就知道该抢哪些 slot |
| **C. 自身状态快照** | 每个节点自身 | 自身持有的 slot、epoch、生效 revision、上次成功上报时间、WAL/队列水位 | 周期性 + 关键事件后 | 重启后判断"我是否已被 fencing"（对比本地 epoch 与 peer/中心视图），避免复活即双主 |

> **C 类最容易被漏掉，但后果最严重**：一个崩溃重启的节点如果只恢复了 A（知道该采什么）而没有 C（不知道自己是否还是 owner），会立刻按 Manifest 全量开采，造成大面积双主。C 类快照 + 重启后强制"先确认归属再采集"的启动契约，是防止这类事故的必要设计。

### 7.2 快照的存储与一致性要求

- **落盘而非仅内存**：三类快照都必须持久化到本地磁盘（建议独立目录，与 TSDB 分离，避免磁盘满时互相影响）。
- **原子写入**：先写临时文件 → fsync → rename。避免进程崩溃时留下半截快照（半截快照比没有快照更危险，因为它看起来可信）。
- **带版本与校验**：每份快照含 `revision / content_hash / written_at / format_version`。启动时校验 hash，校验失败则视为无快照并走 Bootstrap 全量拉取。
- **陈旧度可判**：`written_at` 用于判断快照是否过旧。超过 `T_snapshot_stale`（建议 24 h）时启动告警——说明该区已经很久没和中心同步过了。
- **容量预算**：A 类快照大小 ≈ 全区 target 数 × 每 target 元数据（数百字节）。数万 target 约数 MB~数十 MB，可接受；若单区 target 达十万级，需评估是否按 slot 分片存储或压缩。

### 7.3 启动时的归属确认契约（关键行为约定）

任何 Collector 启动（首次或重启）必须按此顺序，**不允许跳过**：

```
① 读取本地 A/B/C 三类快照，校验 hash
② 尝试连接区内 Coordinator（或 etcd）→ 获取权威归属视图与最新 epoch
   ├─ 成功：以 Coordinator 视图为准；若发现本地 C 中记录的 epoch 已落后
   │        → 认定自己曾被 fencing → 卸载对应 slot → 走 REGISTER/WARMING
   └─ 失败（L3）：向区内 peer 广播查询归属视图
        ├─ 获得多数派一致视图 → 采用之
        └─ 无法获得多数派 → 只恢复【自己明确持有且无争议】的 slot；
                            有争议的 slot 保持不采集并告警（取舍 6：宁可空洞不双主）
③ 加载 Manifest（本地快照优先，若 revision 落后则尝试拉取，拉不到就用旧的并打点陈旧）
④ 仅对【已确认归属属于自己】的 slot 启动抓取
⑤ 上报自身状态 + 快照 revision，进入正常心跳周期
```

第 ② 步的分支逻辑是"主节点维护或网络不通时能自行管理"的核心：它让节点在**没有任何中心组件**的情况下，仍能通过 peer 达成共识并恢复正确的采集范围。

### 7.4 快照与配置陈旧度

L1/L3 期间节点会长期运行在旧 Manifest 上，这本身是可接受的（监控不能停），但必须**可观测**：

- 每节点暴露 `manifest_age_seconds`、`manifest_revision_lag`、`running_on_last_known_good{bool}`。
- 中心侧（恢复后）与区内大盘都要能看到"哪些节点在跑陈旧配置、陈旧多久"。
- 陈旧超过阈值（建议 1 h）升级为告警。长期陈旧意味着新增实例一直没被采集，属于**静默漏采**，比宕机更难发现。

## 8. 任务获取路径与节点标记（对应要求 6）

### 8.1 明确禁止的形态

```
❌ Collector 定时 SELECT * FROM scrape_tasks WHERE zone='A'      （直连业务库）
❌ 每个 Collector 各自高频调用中心接口拉全量任务                   （打爆中心）
```
前者让 DB 成为高频读瓶颈且无法感知漂移；后者在节点数增长时把中心接口打爆，且生效延迟不可控。

### 8.2 四段式路径（v0.2：区分"内容"与"归属"两条通道）

```
【内容通道】—— 低频，走跨区（M1/M2/M3）
① Bootstrap：Agent 启动 → 拉取本区全量 Manifest（revision + hash）→ 写入本地 A 类快照
             → 区内广播给所有 Collector/RC → 各自落盘
② Sync：M3 在线时 push 变更；M3 断开时退化为 M2 digest 自检（30~60 s）
        → 变更原子应用 → 更新快照 → ACK(revision)
③ Reconcile：每 T_reconcile（建议 5 min）上报 revision + hash；不一致才下发增量/全量

【归属通道】—— 高频，区内闭环，绝不跨区
④ Ownership Sync：Coordinator watch 推送（L0/L1/L2）
                   或 peer 互探广告中携带归属摘要（L3，见 §9.3）
⑤ Last-Known-Good：任一通道不可达 → 用本地快照继续运行 + 打点陈旧状态
                   → 恢复后走 ③ / ④ 对账收敛，不做全量覆盖（§3.2 规则 2）
```

**为什么必须分两条通道**：内容变更低频但体积大，适合跨区批量同步；归属变更高频但体积极小（§5.4），必须在区内秒级闭环。把它们混在一条通道里，要么归属变更被跨区延迟拖慢（接管变慢），要么内容同步被高频归属消息挤占（带宽浪费）。

### 8.3 这套设计如何同时满足"不轮询"和"高可用"

- 稳态下 Collector 对中心/DB 的读请求数 ≈ 0：内容由 Agent 代表全区拉取一次，归属由区内推送。
- 对账是低频且带 hash 短路的，成本远低于全量轮询，且仅作兜底。
- LKG 让"协调层故障"退化为"配置不新鲜"而非"监控停摆"——这是监控平台区别于普通业务系统的地方，必须这样设计。

### 8.4 节点标记体系（对应要求 8）

标记分三类，**权威来源单一（中心控制面）**；节点只能上报状态，不能自行修改自己的调度标记，否则会出现互相矛盾的判定。

| 类别 | 标记项 | 用途 |
|---|---|---|
| **生命周期状态** | `REGISTER / WARMING / HEALTHY / SUSPECT / EXPIRED / FENCED / DRAINING / OFFLINE / QUARANTINED` | 驱动调度决策（§15） |
| **能力与容量** | `zone_id / rack / az / capacity_slots / capacity_series / schedulable / version / probe_priority` | 接管候选筛选、均衡计算、版本门禁、**VRRP 优先级计算** |
| **运维意图** | `maintenance(TTL) / quarantined(原因+到期) / pinned(不参与再均衡) / cordoned(不接新slot但保留现有)` | 人工干预与轮动控制 |

**治理三条硬规则：**
1. **运维意图标记必须带 TTL 与责任人**，到期自动回收并提醒。生产环境最常见的事故来源是"某人半年前打的维护标记忘了摘"，导致容量悄悄萎缩。
2. **所有标记变更走审计**；`quarantine 解除`、`批量 drain` 等高危操作要求二次确认或审批。
3. **标记与实际健康度冲突时以协调器/多数派判定为准**，但必须产生告警让人介入（例如打了 maintenance 但节点实际已 EXPIRED）。

`probe_priority` 是本轮新增：它是 VRRP 式确定性认领的输入（§10.2），必须由中心统一分配或按确定性规则推导，**不能让节点自报**（否则节点可以通过调高自己的优先级抢占更多 slot）。

## 9. VRRP 式节点间探测（对应要求 13）

### 9.1 为什么用 VRRP 模型，以及不能照搬的地方

VRRP 的可借鉴之处：**master 周期性广播广告，backup 用 Master_Down_Timer 判定失效，失效后按优先级 + skew time 确定性地选出新 master，无需中心参与**。这套机制天然满足"节点间探测 + 本地自主接管"。

三处必须改造：

| VRRP 原设计 | 本平台的问题 | 改造 |
|---|---|---|
| 单一 master 承载全部流量 | 采集是**分片**的，一个节点持有多个 slot，不同 slot 的接管者可以不同 | 归属粒度下沉到 **slot**：每个 slot 独立走"master/backup"语义，一个节点可以是 slot-1 的 master 同时是 slot-7 的 backup |
| 组播 + 同一广播域 | 跨网区/跨机架组播通常不可用 | 改为**单播 mesh / 部分 mesh**（§9.2） |
| IP 抢占即可生效 | 双采会污染时序数据 | 加 **epoch fencing**（§10.3）+ **相位对齐**（§13.2） |
| 只看广告是否到达 | TCP 通但抓取失败的"灰故障"检测不到 | 探测升级为**应用级健康检查**（§9.5） |

### 9.2 探测拓扑

探测图必须满足：**任一单节点移除后仍连通**（否则有检测盲区）。

| 区内节点数 N | 拓扑 | 说明 |
|---|---|---|
| N ≤ 12 | **全连接 mesh**（每节点探测其余 N−1 个） | 最简单最鲁棒；O(N²) 在 N=12 时仅 132 条探测，开销可忽略 |
| 12 < N ≤ 50 | **部分 mesh**：每节点确定性选择 K=5 个探测对象（按 hash 选，保证图 2-连通）+ **gossip 传播 suspect 状态** | 降低 O(N²) 开销；需校验探测图连通性 |
| N > 50 | **分组探测**：按 rack/az 分组，组内全连接 + 组间代表互探；或引入专职 probe agent | 同时需重新评估单区规模是否应拆分 |

**必须处理非对称连通**：X 能探到 Y 但 Y 探不到 X（单向路由/防火墙问题）是真实存在的。探测结果必须**带方向**上报（`reporter → subject`），中心观测矩阵据此区分"对端挂了"和"我这一侧网络有问题"。

### 9.3 广告报文与归属摘要交换

每次 peer 广告同时承担"我还活着"与"当前归属是什么"两个职责，这是接管能零拉取完成的前提：

```
Advertisement {
  from: node_id, zone_id, term,            // term = 区内成员任期（§10.3）
  state: HEALTHY|SUSPECT|DRAINING|...,
  self_metrics: { held_slots, load_weight, scrape_success_rate,
                  active_series, cpu, mem, disk, wal_lag,
                  manifest_revision, running_on_lkg },
  ownership_digest: hash(sorted[slot_id:epoch:manifest_revision]),  // O(1) 大小
  suspect_list: [ {peer_id, first_missed_at, probe_fail_count} ],   // 我对别人的观测
  probe_priority, capacity_remaining,
  sent_at
}
```

**digest 机制是关键设计**：广告里只放归属的哈希摘要（O(1)），不放完整归属表（O(slots)）。节点间比对 digest，**只有不一致时才交换明细**。这让心跳报文保持在数百字节量级，即使 5 s 一次、50 个节点全连接也不产生可观带宽。

由此，区内每个节点都持有一份**近实时的全区归属视图**（B 类快照，§7.1）——这就是"接管时如何获取对应任务"的答案：**不需要获取，它本来就在本地**。

### 9.4 双向上报与观测矩阵（对应"上报自身状态或探测结果到服务端"）

节点向中心上报两类信息，中心汇聚成矩阵：

```
观测矩阵 M[reporter][subject] = { status, rtt, last_ok_at, fail_count }
自状态向量 S[node] = { state, held_slots, load, manifest_revision, lkg, degradation_level }
```

上报周期 `T_report`（建议 10 s）可以**慢于** peer 探测周期，因为检测决策已在区内本地完成，中心上报只用于观测、审计与仲裁——这是取舍 3 带来的解耦。

**矩阵的四类分析价值（这是"上报探测结果"而不只"上报自己"的真正收益）：**

1. **多数派交叉验证**：X 是否真的挂了，看有多少节点报告 X 不可达。单点报告不足信，多数派报告才定论（§10.1）。
2. **识别异常探测者**：若某节点报告"其他所有人都挂了"，问题大概率在它自己（网卡/路由/进程异常）→ 将其标记为 `probe_untrusted`，其探测结果不计入投票，并对其自身触发健康复查。**没有这一层，一个故障节点的错误观测就能引发全区接管风暴。**
3. **定位非对称故障**：`M[X][Y]=fail` 但 `M[Y][X]=ok` → 网络单向问题，而非节点故障。此时不应接管，应告警排查网络。
4. **区分"节点故障"与"分区"**：若报告 X 不可达的节点集合恰好能被切成两半（一半说 X 挂了、一半说 X 正常），则是网络分区而非 X 故障 → 走分区处理（§10.4）而非接管。

### 9.5 探测层级：必须做应用级，不能只做 TCP

灰故障（gray failure）——进程活着、端口通、但抓取全部失败或 TSDB 写不进去——在真实环境中的占比不低于硬故障，且**只有 TCP 探测时完全检测不到**，后果是该节点持有的所有 slot 静默漏采。

三层探测，逐层加权：

| 层 | 探测内容 | 失败判定 | 权重 |
|---|---|---|---|
| L-a 存活 | TCP 连接 / HTTP 200 | 连续 `N_tcp_fail`（建议 2）次失败 | 触发 SUSPECT |
| L-b 应用健康 | `/health` 返回真实指标：抓取成功率、TSDB 可写、WAL 滞后、reload 是否成功 | 抓取成功率 < 阈值（建议 50%）持续 `T_gray`（建议 30 s），或 TSDB 不可写 | 触发 SUSPECT，且**可单独触发隔离**（§12.4） |
| L-c 金丝雀 | 探测方要求被探方对一个固定的区内 canary target 执行一次真实抓取并返回结果 | 连续 `N_canary_fail`（建议 3）次失败 | 强证据，加速 EXPIRED 判定 |

L-c 是最强证据但成本最高，建议只对**持有高权重 slot 的节点**启用，或降低频率（如 30 s 一次）。

### 9.6 探测参数（建议初值）

| 参数 | 建议初值 | 约束 |
|---|---|---|
| 广告周期 `T_adv` | 5 s | — |
| 单次探测超时 | 2 s，interval 内重试 1 次 | 超时 × 重试 < `T_adv` |
| 失效判定 `T_down` | `3 × T_adv + skew` ≈ 15~17 s | 借鉴 VRRP Master_Down_Timer；容忍单次丢包与短暂 GC |
| SUSPECT 触发 | 错过 1 次广告（5 s） | 仅观察，不变更归属 |
| EXPIRED 触发 | 超过 `T_down` 且**多数派确认** | 才可触发接管 |
| 灰故障阈值 `T_gray` | 30 s | 应用级失败持续时间 |
| 向中心上报 `T_report` | 10 s | 可慢于 `T_adv` |
| 广告抖动 | ±20% 随机化 | 避免同相位造成尖峰 |
| **接管 SLO** | 检测 → 新 owner ACCEPTED **≤ 20 s** | 相比 v0.1 的 60 s 收紧，因检测与认领均已本地化 |

## 10. 归属裁决、epoch 与防脑裂

### 10.1 存活判定的多数派规则

```
判定节点 X 为 EXPIRED 的充要条件：
  ① 本节点连续 T_down 未收到 X 的广告，且 L-b/L-c 探测失败
  ② 从 peer 的 suspect_list / 中心观测矩阵获得确认：
     报告 X 不可达的健康节点数 ≥ quorum = floor(N_zone/2) + 1   （含自己）
  ③ 排除非对称故障：不存在"M[X][*]=ok 且 M[*][X]=fail"的单向特征
  ④ X 未处于 pinned / 已被人工确认维护中的状态
满足 ①②③④ → 本节点可参与对 X 所持 slot 的认领
```

**为什么必须要 ②**：没有多数派要求，一个被隔离的节点会认为"其他所有人都挂了"，进而认领全部 slot → 双主灾难。多数派规则把这种场景转化为"少数派侧不动作、记 UNOWNED、告警"（取舍 6）。

**L1/L3 下 ② 的来源**：中心不可达时，多数派确认完全由 peer 广告的 `suspect_list` 聚合得出——这正是"上报探测结果给同伴"而不仅仅"上报给服务端"的意义：**同伴之间也要互相交换观测**，才能在无中心时完成投票。

### 10.2 确定性认领：优先级 + skew

多数派确认 X 失效后，X 持有的每个 slot 需要确定唯一接管者。借鉴 VRRP 的 skew time 机制，让**各节点独立计算出同一个答案**，无需选举消息往返：

```
每个 slot 的接管者 = argmax over 候选节点 C 的 score(slot, C)

score(slot, C) = w1 × probe_priority(C)              // 中心分配，确定性
               + w2 × capacity_remaining(C)          // 剩余容量，来自广告
               + w3 × affinity(slot, C)              // 同 rack/az 亲和
               − w4 × current_load(C)                // 当前负载，避免压垮
               − w5 × recent_takeover_count(C)       // 抑制同节点连续接管（防雪崩）

候选集 C 的准入条件：
  同 zone ∧ state=HEALTHY ∧ schedulable=true ∧ 版本合规
  ∧ 非 QUARANTINED / pinned ∧ capacity_remaining ≥ slot.weight
  ∧ 已通过 WARMING（新上线节点需满 T_stable）
  ∧ 该 slot 不在其冷却期内（§14.2）

skew 延迟：score 排名越靠后的节点，等待越久才认领
  claim_delay(C) = ((score_max − score(C)) / score_max) × T_adv
  → 排名第一者立即认领；其余节点在延迟窗口内若收到"已有人认领"的广告则放弃
```

**skew 机制的价值**：它把"多方争抢"转化为"有序让位"，无需额外的分布式锁或选举轮次。这与 VRRP 用 skew 保证最高优先级 backup 先成为 master 是同一思路。

**关键前提**：score 的所有输入必须来自**各节点都能看到的一致视图**（广告中的 self_metrics + 中心分配的 probe_priority + 本地 Manifest 中的 rack/az 信息）。若某个输入是节点私有的或不同步的，各节点会算出不同结果 → 双主。这一条是实现时最容易出错的地方，建议在评审时重点检查每个 score 输入的来源。

**候选不足时**：不要强行分配（会压垮健康节点引发连锁故障）。正确动作：slot 记入 `UNOWNED` + **最高级告警** + 触发扩容建议 + 若配置了兜底采集（如主机侧 agent）则启用并标记为降级数据源。

### 10.3 epoch 与 fencing：中心不可用时如何推进

epoch 是防脑裂的核心令牌，但 L3 下没有中心签发者。解决方案是**复合 epoch + 成员任期**：

```
fencing_token = (zone_term, slot_epoch)

zone_term：区内成员视图的任期号
  - 每次"多数派确认的成员集合发生变化"时 +1
  - 由多数派共同推进：只有获得 quorum 确认的节点才能提升 term
  - 持久化到本地（C 类快照），重启不回退
  → 少数派侧无法推进 term，因此其签发的 token 天然低于多数派侧

slot_epoch：单个 slot 的归属变更序号
  - 每次认领 +1
  - L0/L1/L2 由 Coordinator 签发；L3 由认领节点在提升后的 term 下自行 +1
```

**三层防护（缺一不可）：**

1. **token 单调递增且持久化**：`(zone_term, slot_epoch)` 按字典序比较；本地持久化，重启不回退。
2. **下游拒绝旧 token**：Coordinator/中心只接受 ≥ 当前记录值的上报；统一 remote-write 场景下，存储侧/网关按 `(series, collector_id)` 去重。
3. **旧 owner 自我卸载（行为契约）**：X 恢复后收到的第一份广告或 Coordinator 响应中包含当前 `(zone_term, slot_epoch)`。若发现自己持有的 token 落后，**必须立即停止该 slot 抓取、卸载配置、进入 FENCED**，然后重走 REGISTER→WARMING。
   → 这条必须写进 Collector 的行为契约并在测试中覆盖，**不能只依赖中心拒绝**：因为 X 的抓取会先污染本地 TSDB 与（若有）remote-write 队列，中心拒绝上报并不能撤销已产生的副作用。

**为什么需要 zone_term 而不能只用 slot_epoch**：分区场景下，两侧可能同时对同一 slot 做 +1，产生相同的 `slot_epoch`。有了 term，多数派侧的 term 更高，其 token 天然胜出，少数派侧的写入会被拒绝。这是把"quorum"从存活判定延伸到 fencing 的必然结果。

### 10.4 网络分区处理

```
区内发生分区（部分节点互相不可达）：
① 各侧独立统计"我能看到的健康节点数"
② 多数派侧（≥ quorum）：正常运作，可对少数派侧节点执行 EXPIRED 判定与接管
③ 少数派侧（< quorum）：
   - 【不接管】任何 slot（取舍 6）
   - 继续采集自己已持有的 slot（数据不断，且是有效数据）
   - 无法推进 zone_term → 其 epoch 落后 → 上报会被多数派侧/中心拒绝
   - 打点 partition_minority=true，最高级告警
④ 分区恢复：
   - 少数派侧比对 term，发现自己落后 → 对被多数派侧接管的 slot 执行自我卸载
   - 归属既成事实被承认（§3.2 规则 2）→ 少数派侧节点走 WARMING 回归
   - 由再均衡决定是否把部分 slot 迁回（§14.3：不物归原主）
   - 数据空洞：少数派侧持有的 slot 无空洞；被接管的 slot 空洞 ≤ 1 抓取周期
```

**特别说明**：③ 中"继续采集自己已持有的 slot"是有意的设计。少数派侧节点本身是健康的、能访问 target 的，让它停采只会扩大空洞。它无法推进 term，所以不会产生被承认的新归属，双采由取舍 4 的 at-least-once + 去重兜底。

### 10.5 特殊场景：2 节点网区

N=2 时 quorum=2，任一节点故障都无法达成多数派 → **无法自动接管**。这是数学上的必然，不是实现缺陷。三个应对选项，必须显式选一个：

| 选项 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 部署 ≥ 3 个 collector | 容量成本；但这是唯一能真正自动容灾的方案 |
| B | 引入**区内 witness**（轻量仲裁进程，不参与采集，只投票），N=2+1 → quorum=2 | 需额外部署与运维一个组件；witness 本身也要考虑 HA |
| C | 2 节点区**不做自动接管**，故障时告警 + 人工介入；或允许中心在可达时充当第三票 | 有空洞且依赖人工/跨区链路，与 L3 自治目标冲突 |

**建议**：新建网区一律按 A（≥3 节点）规划；存量 2 节点区若无法扩容，用 B。选 C 必须在设计评审时明确记录为已接受的风险。

## 11. 归属可发现性（对应要求 14："如何知道哪些任务被分配到哪个节点"）

### 11.1 五个查询维度

| 维度 | 查询 | 回答的问题 | 数据来源 |
|---|---|---|---|
| **实例 → 归属** | `instance_id` | 这个实例由哪个区、哪个 collector、哪个 slot 在采？从何时起？生效哪个 revision？ | Manifest（instance→slot）+ 归属视图（slot→owner） |
| **节点 → 任务** | `collector_id` | 这个节点持有哪些 slot、多少 target、总权重、当前负载？ | 归属视图 + 该节点自状态上报 |
| **网区 → 全景** | `zone_id` | 全区 slot→owner 映射、UNOWNED 列表、各节点负载、digest、降级级别 | 区内归属视图（任一节点可答）+ 中心归属注册表 |
| **slot → 历史** | `slot_id` | 这个 slot 的归属变更审计轨迹（谁→谁、何时、什么原因、epoch） | 中心归属注册表（含历史区间） |
| **时点 → 归属** | `instance_id + timestamp` | **T 时刻**这个实例由谁在采？ | 归属历史表（`valid_from / valid_to` 区间） |

**第五个维度（时点查询）最有价值也最容易被漏掉**：故障复盘时最常见的两个问题是"那段数据为什么缺了"和"当时是谁在采"。没有时点归属查询，就只能靠日志翻找，且日志往往已滚动丢失。实现上要求归属注册表**保留变更历史区间**而非只存当前值，保留期建议 ≥ 数据保留周期。

### 11.2 中心不可达时也要能查

要求 14 隐含一个关键点：**驱离/接管往往发生在异常期间，而此时中心可能正好不可达**。所以归属信息不能只在中心：

- 区内**任一** Collector 都能回答"全区归属全景"（因为 B 类快照 + peer 广告摘要，§7.1/§9.3）。
- 提供区内本地查询入口（每节点暴露 `/ownership` 只读接口），运维在中心挂掉时仍能定位任务分布。
- 中心归属注册表与区内视图**通过 digest 对账**：不一致时以"多数派区内视图"为既成事实，中心补登记（§3.2 规则 2）。

### 11.3 驱离/接管时如何拿到对应任务（要求 14 的直接答案）

```
接管场景（非计划，X 已失联）：
  ① Y 通过多数派确认 X EXPIRED（§10.1）
  ② Y 从【本地 B 类快照 + 最后一批 peer 广告】得知 X 持有哪些 slot（无需询问任何人）
  ③ Y 从【本地 A 类快照 = 全区 Manifest】取出这些 slot 的 target 定义（无需拉取）
  ④ Y 计算 score 确认自己是接管者（§10.2），提升 token（§10.3）
  ⑤ Y 立即执行一次 catch-up 抓取（§13.3）+ 按相位对齐排定后续抓取
  → 全程零外部请求，时延 = 检测时延 + 认领时延 ≈ T_down + 秒级

驱离场景（计划内，X 仍健康）：
  ① 运维发起 drain → 打标 maintenance(TTL) → X 置 DRAINING（停止接受新 slot）
  ② 编排方（Coordinator 或 L3 下的节点协商）从归属视图取得 X 的 slot 清单
  ③ 按批次为每个 slot 选定接管者（同一套 score 函数）
  ④ make-before-break：接管者预加载（Manifest 本地已有 → 只需就绪检查）
     → 就绪后签发新 token → X 停采 → Y 开采（§12.2）
  ⑤ X 全部迁出 + 静默期（WAL flush、remote-write 队列排空）→ OFFLINE
```

**注意 ③ 中"接管者预加载"在取舍 2 下变得极轻**：因为 Y 本来就持有全部 target 定义，预加载只剩"建立连接池、确认 TSDB 可写、计算相位"，不再有配置传输。这是数据连续性得以最大化的结构性原因。

## 12. 接管与驱离

### 12.1 两者的本质区别

| 维度 | 驱离 Drain | 接管 Takeover |
|---|---|---|
| 触发 | **计划内**（维护、升级、缩容、轮动） | **非计划**（故障、失联、灰故障） |
| 节点状态 | 健康、可通信 | 已失联或不可信 |
| 归属信息获取 | 直接问 X（它自己最清楚） | 从本地快照 + peer 摘要（X 问不到） |
| 迁移方式 | make-before-break，**先建后拆** | 直接认领，token 提升，旧 owner 事后 fencing |
| 数据空洞 | 可做到 ≈ 0（预加载 + 相位对齐 + 重叠双采） | ≤ 1 抓取周期，catch-up 后可降至秒级 |
| 节奏 | 受控、渐进、可暂停 | 尽快，但有并发上限 |
| 完成判据 | slot 全部迁出 + WAL flush + 队列排空 + 无在途抓取 | 新 owner ACCEPTED + token 生效 |

**这个区别必须体现在实现里**：把维护当故障处理会造成不必要空洞；把故障当维护处理会造成接管超时。

### 12.2 make-before-break 时序（驱离与计划内迁移共用）

```
① 编排方决定 slot-S 从 X 迁往 Y
② 标记 X: slot-S = HANDOFF_PENDING；Y: slot-S = WARMING
③ Y 就绪检查：能连通 target（Manifest 本地已有）/ TSDB 可写 / 配额充足 / 相位已计算
④ Y 回 READY
⑤ 编排方对 slot-S 签发新 token（term 不变，slot_epoch+1），归属改为 Y，通知 X
⑥ X 停止抓取（保留已采数据可读，不删 TSDB）
   Y 立即执行一次 catch-up 抓取，随后按对齐相位进入正常调度
⑦ 双方 ACK → 标记完成 → 记录审计（含实测空洞窗口）
⑧ 失败回滚：任一步超时/失败 → 撤销 token 变更 → slot-S 仍由 X 持有 → 记录失败原因
```

**第 ⑥ 步的重叠窗口是有意的**：允许 X 与 Y 在 ≤1 个抓取周期内同时采集，配合相位对齐与查询侧去重（§13.2），可把空洞压到 0。这是取舍 4（at-least-once）换来的直接收益。

### 12.3 驱离流程与护栏

```
① drain 请求（collector_id + 原因 + 预期时长）→ 审批 → 打标 maintenance(TTL = 预期时长 × 2)
② 置 DRAINING：立即移出接管候选池（不再接新 slot），保留现有 slot 继续采集
③ 计算迁出计划：按 slot 权重降序分批，每批 ≤ max_concurrent_migrations，批间隔 T_batch
④ 逐批 make-before-break（§12.2）
⑤ 全部迁出 → 静默期 T_quiesce：等在途抓取完成、WAL 落盘、remote-write 队列排空
⑥ 置 OFFLINE → 摘标记 → 允许停机/升级
⑦ 回归：REGISTER → WARMING → 由 §14 决定是否分回 slot（不物归原主）
```

**四条护栏（必须显式实现）：**
1. **区内最后一个健康节点拒绝驱离** → 否则整区监控归零。拒绝并告警。
2. **TTL 到期仍在 DRAINING** → 告警 + 提醒延期或结束，**不自动强制停机**。
3. **迁出中对端连续失败** → 暂停驱离、保留原节点采集、告警人工介入。宁可维护延期，不可监控中断。
4. **驱离中发生真实故障** → 立即中止 drain，该节点恢复 schedulable 并优先参与接管（此时可用性优先于维护计划）。

### 12.4 隔离（quarantine）

用于"节点活着但行为异常"：抓取成功率骤降、TSDB 写失败、版本不合规、上报数据明显异常、被识别为 `probe_untrusted`（§9.4）。
与故障接管的差别：节点仍可通信，所以**可以走优雅 make-before-break**，不必抢占，空洞接近 0。隔离后不参与任何调度，解除需人工审批 + 复检通过。

## 13. 数据连续性预算与增强手段（对应要求 14 后半）

### 13.1 各场景空洞预算

这张表应当作为验收标准，也是向业务方解释"监控数据为什么会缺"的依据。

| 场景 | 检测时延 | 认领时延 | 预期数据空洞 | 备注 |
|---|---|---|---|---|
| **优雅驱离**（make-before-break + 相位对齐 + 重叠双采） | — | — | **≈ 0** | 重叠窗口内双采，查询侧去重 |
| **计划内迁移/再均衡** | — | — | **≈ 0** | 同上 |
| **进程崩溃**（主机存活） | ≤ `T_down` ≈ 15~17 s | 秒级（本地已有清单） | ≤ 1 抓取周期；**catch-up 后可降至秒级** | 若磁盘可读，可选 WAL 回填进一步压缩 |
| **主机宕机/失联** | ≤ `T_down` | 秒级 | ≤ 1 抓取周期 + catch-up | 磁盘不可读，无法回填 |
| **灰故障**（TCP 通但抓取失败） | ≤ `T_gray` ≈ 30~60 s | 秒级 | ≤ 1~2 抓取周期 | 检测慢是主因 → L-b/L-c 探测的价值 |
| **中心 + 协调器全失联（L3）** | 区内 peer 照常 | 照常 | **≈ 0（无额外影响）** | 要求 12 的验收点 |
| **网区被隔离，区内多数派存活** | 照常 | 照常 | **≈ 0** | 区内自治生效 |
| **Coordinator 主节点维护中（L2）** | 照常 | 备节点接管后照常 | ≈ 0（切换期 <`T_coord_failover` 内暂停迁移） | 检测不依赖 Coordinator |
| **区内节点数 < quorum** | — | **不接管** | **空洞持续到人工介入** | 取舍 6，必须显式接受并告警 |
| **网区调整**（实例换区） | — | — | 双写窗口内 ≈ 0 | §18.4 |

### 13.2 相位对齐（性价比最高的连续性手段）

**问题**：Prometheus 默认对每个 target 的抓取时刻带有节点级随机偏移。X 在 `t=0,60,120...` 抓取，Y 接管后可能在 `t=37,97,157...` 抓取 → 时间轴上出现 37 s 的空洞 + 采样间隔紊乱，即使双方都在正常工作。

**解法**：抓取相位由 **target 自身属性确定性推导**，而非节点随机生成：

```
scrape_offset(target) = hash(target.addr, slot.offset_seed, interval) mod interval
```

由于 `offset_seed` 来自 Manifest（全区一致），任何节点接手同一 target 都会算出**相同的抓取时刻**。于是 X 与 Y 的采样点在时间轴上重合，重叠窗口内的双采变成**同一时刻的重复样本**（去重即可），而不是错开的空洞 + 冗余。

**配套要求：**
- 去重规则：同 `(series, timestamp)` 保留任一（或按 `collector_id` 优先级保留），需在查询侧/存储侧显式实现。
- 若使用统一 remote-write，`collector_id` 标签必须在采集侧就打上（取舍 4）。
- Manifest 变更导致 `offset_seed` 变化时，会引发一次全区相位重排 → 应尽量避免频繁变更 seed，或在变更时安排重叠窗口。

### 13.3 catch-up 抓取（立竿见影）

新 owner 认领 slot 后，**不等下一个调度时刻，立即对全部接管的 target 执行一次带外抓取**。
→ 把空洞从"最多 1 个 interval"压缩到"一次抓取耗时"（通常秒级）。interval 越长（如 5 min），这个手段的收益越大——否则接管后要等最多 5 分钟才有第一个样本。

**注意**：catch-up 抓取应限流（分批、并发上限），避免接管 200 个 target 时瞬间打满网络/CPU 或压垮被监控端。建议按 slot 分批，批内并发受 `max_catchup_concurrency` 限制。

### 13.4 连接预热（谨慎使用）

由于每个节点持有全区 Manifest，理论上可以为**所有**区内 target（不只自己负责的）维持 warm 连接池与 DNS 缓存，使接管时不付 TCP/TLS 握手成本。
- **收益**：接管首个样本更快，catch-up 更平滑。
- **风险与约束**：必须严格限定为"仅建连、不抓取"。否则等于变相双采，且会对被监控端造成额外压力。建议只对**高权重 slot / 关键实例**启用，并设置连接池上限与空闲回收。
- **建议**：作为可选优化项，在阶段 3 评估，不要一开始就上（复杂度与误采集风险）。

### 13.5 WAL 回填（可选，仅特定场景）

若故障节点**主机存活、磁盘可读**（进程崩溃、OOM、容器重启），其本地 TSDB 的 WAL 与已落盘 block 中含有"接管前最后一段时间"的数据。可由恢复任务读取并回填到长期存储/新 owner。
- **前提**：需要节点间磁盘可访问，或共享存储，或故障节点能被修复后重启并自行补传。
- **适用**：仅进程级故障；主机彻底损毁时无效。
- **建议**：列为可选增强，不纳入阶段 1 范围。若不做，须在空洞预算中如实体现（§13.1 已体现）。

### 13.6 remote-write 队列保全

- **优雅驱离**：静默期 `T_quiesce` 内必须等待发送队列排空后才允许停机（§12.3 ⑤）。
- **崩溃**：未发送的队列内容丢失，**暴露量 = 队列缓冲时长**。因此队列容量应按"可容忍的最大空洞"反推设定（如希望崩溃时最多丢 5 min 数据，队列至少缓冲 5 min），并暴露 `remote_write_queue_depth / oldest_sample_age` 指标 + 告警。
- 这条常被忽略：很多人以为有 remote-write 就万无一失，实际上队列缓冲时长直接等于崩溃场景的数据丢失上限。

### 13.7 展示层必须显式标注空洞

时序断裂处**不得静默插值**。静默插值会让运维基于假数据做判断，比数据缺失更危险。
- 已知空洞（接管/迁移记录在案）：按审计记录标注区间与原因。
- 未知空洞：按采样间隔的 N 倍无数据判定并标注"数据缺失"。
- 跨 slot 迁移导致的分段数据：由 Zone Query Proxy 拼接并标注接缝（§17.2）。

## 14. 上线后均衡与归还

### 14.1 触发条件

| 触发源 | 判定 |
|---|---|
| 节点上线 | 完成 WARMING 且 `schedulable=true`，持续 `T_stable`（建议 5 min）后进入评估 |
| 节点故障恢复 | 从 FENCED/EXPIRED 恢复并完成 WARMING 后评估 |
| 容量漂移 | 任一节点负载权重偏离目标 > `threshold_imbalance`（建议 20%）且持续 `T_imbalance`（建议 10 min） |
| slot 权重变化 | Manifest 变更导致权重显著变化 → 全局重算 |
| 人工计划 | 轮动、扩容、缩容、网区调整（§18） |
| 降级恢复 | 从 L1/L2/L3 回到 L0 后的收敛性再均衡（低优先级，避免恢复瞬间抖动） |

### 14.2 三重抑制（防止迁移风暴的核心）

没有抑制的自动再均衡会在真实环境造成周期性监控抖动，比不均衡本身更伤。

1. **迟滞**：进入阈值（20% 偏差）必须显著高于退出阈值（建议 8%）。否则系统在阈值附近反复进出均衡态，持续迁移。
2. **冷却**：单节点完成一次迁入/迁出后进入 `T_cooldown`（建议 15 min）；全局并发迁移 slot 数 ≤ `max_concurrent_migrations`（建议 ≤ 区内 collector 数 × 10%）。
3. **渐进**：每轮只迁移"消除最大偏差所需的最小 slot 集合"，重新观测后再决定是否继续。宁可分 3 轮达到均衡，也不要 1 轮迁 40 个 slot。

**额外硬约束：**
- `pinned` / `maintenance` / `quarantined` 节点持有的 slot **不参与自动再均衡**。
- 单节点每轮迁出比例 ≤ `max_drain_ratio`（建议 25%）。
- 再均衡可随时人工 `pause`，暂停状态需持久化（Coordinator 重启后仍生效）。
- **L3 下再均衡完全冻结**：无协调器时不做主动优化，只维持既有归属 + 故障接管。避免分布式节点各自优化导致互相打架。

### 14.3 均衡目标函数

```
最小化：  Σ |load(i) − target_share(i)|                 （负载偏差，主目标）
约束：    load(i) ≤ capacity(i)                          （不超容量）
          同 zone 内分配（禁止跨区）
代价项：  + λ × 迁移 slot 数                              （迁移有成本）
          + μ × 受影响的高权重 slot 数                     （重要 target 少动）
亲和项：  − ν × 同 rack/az 聚合收益                        （降低跨机架流量）
```

λ、μ、ν 需按压测调参。**"归还"的正确语义**：故障节点恢复后不应无条件拿回原 slot。理由：① 接管方已建立 TSDB 数据，归还会造成时序二次断裂；② 原节点刚经历异常，立即回灌负载有风险。
→ 归还应作为**普通再均衡的一次输入**（把恢复节点视为新增容量），由算法决定是否迁移、迁移多少。这一点与直觉相反，建议评审时明确写进设计共识。

## 15. 节点状态机

```
                          ┌────────────┐
        首次注册 / 恢复注册 │  REGISTER  │
                          └─────┬──────┘
                                │ 准入检查通过 + 启动归属确认契约(§7.3)完成
                                │ (版本合规/容量可探测/健康探针OK/zone匹配/无争议slot已确认)
                                ▼
                          ┌────────────┐   观察期满 T_warm    ┌────────────┐
                          │  WARMING   │ ───────────────────► │  HEALTHY   │
                          │(不接新slot, │                      │ (可被分配,  │
                          │ 预加载+建连)│                       │ 参与互探投票)│
                          └────────────┘                      └─────┬──────┘
                                ▲                                   │ 错过 1 次广告(5s)
                                │ 迁入 slot(make-before-break)        │ 或 L-b 应用级异常
                                │                                   ▼
                          ┌─────┴───────┐  再均衡中仍健康      ┌────────────┐
                          │ REBALANCING │ ◄─────────────────── │  SUSPECT   │
                          │ (叠加标记)   │                      │(观察+发起投票│
                          └─────────────┘                      │ 不变更归属) │
                                                               └─────┬──────┘
                                                                     │ T_down 超时
                          ┌────────────┐  打标维护(带TTL)              │ + 多数派确认
                          │  DRAINING  │ ◄──────────────────┐        ▼
                          │ (只出不进)  │                    │  ┌────────────┐
                          └─────┬──────┘                    │  │  EXPIRED   │
                                │ slot 全部迁出               │  │(所持slot可被│
                                │ + WAL flush + 队列排空       │  │ 认领)      │
                                ▼                            │  └─────┬──────┘
                          ┌────────────┐                      │        │ token 被提升
                          │  OFFLINE   │                      │        ▼
                          └────────────┘                      │  ┌────────────┐
                                                              │  │   FENCED   │
                                                              │  │(旧owner作废,│
                                                              │  │ 自我卸载)   │
                                                              │  └─────┬──────┘
                                                              │        │ 恢复+归属确认
                                                              │        ▼
                                                              │   回到 REGISTER/WARMING
                                                              │
  ┌──────────────┐  滑动窗口内状态翻转 > N_flap(建议3次/10min)   │
  │ QUARANTINED  │ ◄─────────────────────────────────────────┴────
  │ (不参与调度)  │  或 被识别为 probe_untrusted(§9.4)
  │              │  解除：人工审批 或 冷却期满(建议≥30min)+复检通过
  └──────────────┘
```

**语义要点：**
- `SUSPECT` 是**必需的中间态**。"错过一次心跳就接管"会让网络抖动引发大规模无谓迁移。SUSPECT 期间只观察、发起投票，不变更归属。
- `WARMING` 不接受新 slot，但会预加载配置、建立连接、完成 TSDB 就绪检查——避免"刚接管就压垮新节点"。在取舍 2 下 WARMING 的成本大幅降低（配置本地已有），主要是连接与就绪检查。
- `QUARANTINED` 抑制 flapping 放大效应：反复故障的节点若一直参与调度会引发接管风暴，把健康节点也拖垮。新增触发源：`probe_untrusted`（观测矩阵识别出的异常探测者）。
- `REBALANCING` 不是独立健康状态，而是叠加标记，让再均衡可观测、可暂停。
- **状态判定权**：L0/L1/L2 由 Coordinator 汇总多数派投票后确定；L3 由各节点基于多数派共识自行确定，并通过广告互相通告以保持一致。

## 16. rulecheck 规则路由与 rc 调度域（对应要求 3）

### 16.1 设计原则

**规则必须在数据所在的网区内执行**：跨区查询时序在隔离网络下不可行或代价极高；告警评估对延迟敏感；规则中心故障不应影响存量告警能力（区内自治）。

### 16.2 调度域模型

rc 与 collector **共享同一套网区调度域框架，但独立分组**：

```
Zone
 ├─ CollectorGroup: slot 分配（抓取任务）
 └─ RCGroup:        rule_slot 分配（巡检规则）
```

不复用同一组 slot 的原因：规则评估的负载特征（查询 QPS、表达式复杂度、时间窗口长度）与抓取完全不同，规则数与 target 数比例也不固定，共用会互相挤压。
但**共用**网区注册表、VRRP 互探、多数派投票、租约/epoch 模型、状态机与再均衡框架——只把"分配什么资源"参数化，避免实现两套调度逻辑。rc 同样持有全区规则清单快照，同样支持 L3 自治认领。

### 16.3 规则包切分与下发

```
RuleSpec (逻辑规则, 含 selector)
    │ selector 展开 → 实例集 → 按 zone 分组
    ▼
ZoneRulePackage { zone_id, rule_group_name, rules[], target_scope[],
                  eval_interval, spec_revision, content_hash, term }
    │ 按 rule_slot 切分（以 rule group 为最小单位）
    ▼
RC 实例（同 zone 内）
```

- **rule group 是最小分配单位**，不拆散组内规则——同组规则通常共享评估周期与依赖，拆散会造成评估时序不一致。
- 目标集很大时按 target 分片，一个 group 可由多个 rc 分担，每分片带独立 token。
- 下发路径复用 §8.2（内容通道走跨区，归属通道区内闭环）。**rc 不直连业务库**。

### 16.4 rc 高可用要点

- rc 失联接管与 collector 同构（互探 → 多数派 → 确定性认领 → token 提升 → 认领即评估）。
- **告警去重**：接管窗口内新旧 rc 可能同时评估同一规则产生重复告警。需在告警汇聚层按 `(rule_id, instance, fingerprint, term窗口)` 去重；或让新 rc 评估前先读取上一任的告警状态（取决于告警状态存哪里——§22 待拍板项）。
- **数据空洞导致误告警**：rc 依赖区内数据源，而数据源本身可能正在接管中。rc 查询必须容忍部分数据缺失，避免产生"实例消失"类误告警 → 对 `up`/缺失类告警增加持续时间条件（`for`），且 **`for` 应 ≥ 接管 SLO（20 s）+ 1 个抓取周期**。
- 相位对齐（§13.2）间接改善 rc 稳定性：采样时刻跨节点一致，rc 的 `rate()`/`increase()` 计算不会因接管而出现窗口错位。

## 17. 数据展示与查询路由（对应要求 4）

### 17.1 路由链路

```
用户查看实例 i 的指标
   ▼
展示层 → 查询网关：query(instance=i, metric=m, range=[t1,t2])
   ▼
网关解析：实例台账(i) → zone_id = Z     ← 路由表本地缓存 + 订阅/自检更新（§4.3、§6）
   ▼
网关 → Zone Z 的 Query Proxy（复用该区跨区通道，M1/M3 下无需入向开口）
   ▼
Proxy 聚合区内数据源：
   - slot 历史迁移 ⇒ 同一 target 数据可能分散在多个 collector 的本地 TSDB
   - 用【时点归属查询】(§11.1 维度5) 确定 range 内各时段的 owner
   - 并发查询相关端点 → 按 series 合并 → 时间轴拼接/去重
   ▼
网关 merge（跨区场景）→ 展示层渲染（含空洞标注，§13.7）
```

**时点归属查询在这里是刚需**：没有它，Proxy 只能盲目查询区内所有 collector，浪费且慢；有了它，可以精准定位"t1~t2 期间这个 target 的数据分别在哪几个节点上"。这是 §11.1 第五维度的第二个用途（第一个是故障复盘）。

### 17.2 必须处理的四个查询难题

1. **时序断裂**：slot 迁移导致同一 series 在不同 TSDB 中分段。Proxy 按时点归属向多个端点查询并拼接，接缝处可能有空洞 → **显式标注，不静默插值**（§13.7）。
2. **双采去重**：at-least-once 下接管窗口有重复样本。若带 `collector_id` 标签，去重需在查询侧显式做（聚合时忽略该标签）。**标签设计要在上线前定死**。
3. **部分失败降级**：某端点不可达时返回**部分数据 + 数据源可用性标注**，而不是整体报错或静默返回残缺曲线。
4. **时钟偏差**：多区数据合并时各区 NTP 偏差会造成曲线错位。统一以 UTC 存储，展示层按用户时区渲染，跨区图表标注数据源区域。

### 17.3 全局视图的取舍

| 方案 | 说明 | 适用 |
|---|---|---|
| **联邦查询（推荐主路径）** | 网关实时 fan-out 到各区，不搬运数据 | 交互式排障、实例级下钻；新鲜度最高 |
| **中心长期存储（可选补充）** | 各区 remote-write 到中心统一长期存储 | 跨区趋势对比、长周期容量分析、统一告警台 |
| **仅摘要上报（低成本）** | 各区只上报聚合指标（可用率、抓取成功率、告警计数） | 全局健康大盘；不承载明细查询 |

推荐：**联邦查询做明细 + 摘要上报做全局大盘**。是否引入中心长期存储取决于是否有强跨区分析需求——它带来样本量与带宽成本，且引入去重复杂度（取舍 4），不建议无条件上。

## 18. 优雅轮动设计（对应要求 8）

### 18.1 轮动场景分类

| 场景 | 特征 | 策略 |
|---|---|---|
| 滚动升级 | 区内节点逐个升级，需保容量 | 逐节点 drain → 升级 → 回归 → 下一个 |
| 机架/AZ 迁移 | 整批搬迁 | 分批 drain，保证每批后剩余容量 ≥ 峰值 × 1.3 |
| 扩缩容 | 容量变化 | 扩容：WARMING 后再均衡；缩容：drain 后永久移除 |
| 硬件更换 | 单节点长期不可用 | 接管 → 长期不归还 → 新硬件走扩容流程 |
| **协调器主节点维护** | Coordinator 主节点停机 | 备节点接管（L2）；若主备同时维护 → 进入 L3，冻结再均衡与配置变更 |
| 网区调整 | 实例归属网区变化 | §18.4（最高风险） |

### 18.2 滚动升级的容量护栏

```
区内 collector 总数 N，单节点承载 ≈ 总负载/N
批次大小 B 需满足：(N − B) × 单节点容量 × 安全系数(0.8) ≥ 总负载
   → N=3 时 B=1；N=6 时 B≤2
每批：drain(batch) → 全部迁出且静默期结束 → 升级 → 健康检查 → WARMING
      → 观察 T_obs(10 min) → 观察期内无异常才允许下一批
硬性熔断：过程中出现 UNOWNED slot 或抓取成功率下降 > 阈值 → 立即暂停并回滚当前批
```

**关键**：批次间必须有观察期，且观察期指标（抓取成功率、告警数量、数据空洞、UNOWNED slot 数）作为下一批的准入门禁。"升级完立刻下一批"是滚动升级最常见的翻车方式。

### 18.3 版本门禁

- 注册表记录每节点 `version`，中心维护"允许版本集合"。
- 版本不合规节点：**不接受新 slot**，但保留现有 slot（避免升级期采集空洞），并告警提示需轮动。
- 混合版本期间必须确认新版本能解析旧 Manifest 格式 → **下发协议向前兼容**（新增字段可选、旧字段不删除）。
- peer 互探广告格式同样要向前兼容，否则混合版本期间探测会失败并误判节点故障——这是 VRRP 式互探引入的新兼容性风险点，需专门测试。

### 18.4 网区调整（最高风险，需专项流程）

实例从 Zone A 迁到 Zone B，意味着采集权跨区转移、历史数据留在 A、新数据在 B、规则包需一增一删且不能"两边都评估"或"两边都不评估"。

采用**双写窗口 + 单向切换**：

```
① 台账变更审批（记录 effective_at 与新旧 zone，保留双向路由条目）
② 在 B 区 Manifest 中加入该 target（预热，暂不启用采集）
③ 到达 effective_at：
   - B 区开始采集（token 起算）
   - A 区标记该 target DEPRECATED，继续采集 T_overlap（2 × 抓取周期）
④ T_overlap 结束：A 区停止采集并从 Manifest 移除
⑤ 查询路由保留 A/B 双条目，按时间边界拼接（t < effective_at 查 A，t ≥ 查 B）
⑥ 保留期（≥ 数据保留周期）结束后清理 A 侧路由条目
```

## 19. 可观测性与运维接口

### 19.1 平台自监控指标

| 类别 | 指标 |
|---|---|
| **降级状态** | `degradation_level`(L0~L3) 每区、进入/退出事件、持续时长 |
| **探测健康** | peer 探测成功率、非对称失败对数、`probe_untrusted` 节点数、观测矩阵完整度 |
| **归属健康** | 各区 UNOWNED slot 数、多数派投票次数与结果、归属 digest 不一致次数、区内视图 vs 中心注册表偏差 |
| **token/fencing** | `zone_term` 当前值与推进次数、**收到旧 token 上报的次数**、自我卸载触发次数 |
| **快照与配置新鲜度** | 三类快照 hash 校验失败次数、`manifest_age_seconds`、`manifest_revision_lag`、`running_on_lkg` 节点数 |
| **调度** | slot 迁移速率、迁移成功率、接管时延分位（检测→ACCEPTED）、再均衡暂停状态、冷却中节点数 |
| **数据连续性** | **实测空洞时长**（每次接管/迁移记录）、catch-up 抓取耗时与成功率、重叠双采样本数、remote-write 队列 `oldest_sample_age` |
| **采集质量** | 抓取成功率、抓取延迟分位、活跃序列数、TSDB 磁盘水位、WAL 大小 |
| **通道** | 跨区通道模式（M1/M2/M3）与当前状态、长连接重连次数、push 延迟、ACK 超时率、digest 自检命中率 |

**四个最有价值但最容易被忽略的指标**（建议配独立告警）：
- `收到旧 token 上报的次数` —— 直接反映脑裂风险正在发生。
- `running_on_lkg 节点数` / `manifest_age_seconds` —— 反映中心是否已悄悄失效、是否有静默漏采。
- `probe_untrusted 节点数` —— 反映探测层自身是否可信，是接管风暴的前兆。
- `UNOWNED slot 数` —— 直接等于当前的监控盲区大小。

### 19.2 运维接口

| 操作 | 说明 | 保护 |
|---|---|---|
| `show ownership(zone)` | 输出 slot→owner 全景、token、digest、UNOWNED 列表 | 只读；**区内任一节点可答**（中心挂掉时仍可用，§11.2） |
| `show ownership(instance, at=T)` | 时点归属查询 | 只读；用于复盘与查询路由 |
| `show probe-matrix(zone)` | 输出 N×N 观测矩阵与非对称失败对 | 只读 |
| `drain(collector, reason, duration)` | 计划性驱离 | 审批 + 最后健康节点拒绝 + TTL |
| `undrain(collector)` | 中止驱离回归调度 | 审计 |
| `quarantine / unquarantine` | 隔离与解除 | 解除需审批 + 复检 |
| `pause / resume rebalance(zone)` | 暂停再均衡 | 状态持久化 |
| `pin / unpin(slot|collector)` | 冻结分配 | TTL + 到期提醒 |
| `force-takeover(slot, target)` | 人工强制迁移 | 二次确认 + 记录理由 |
| `reconcile(zone)` | 触发强制对账 | 限流 |
| `set-degradation(zone, level)` | 人工强制降级/恢复（演练用） | 审批；演练必备 |
| **`simulate(plan)`** | 迁移/轮动计划预演，输出影响面（迁移 slot 数、预计空洞、容量变化、quorum 是否满足） | **强烈建议实现**，显著降低变更风险 |

## 20. 风险清单与缓解

| # | 风险 | 后果 | 缓解 |
|---|---|---|---|
| R1 | 脑裂双主（GC 停顿/分区后旧 owner 复活） | 重复采集、样本冲突、告警重复 | 复合 token `(zone_term, slot_epoch)` 三层防护（§10.3）+ 旧 owner 自我卸载契约 + **启动归属确认契约**（§7.3） |
| R2 | 单节点错误观测引发接管风暴 | 健康节点被误判、大面积无谓迁移 | 多数派投票（§10.1）+ 观测矩阵识别 `probe_untrusted`（§9.4）+ flapping 隔离 |
| R3 | 再均衡风暴（阈值抖动、无冷却） | 持续迁移、TSDB 反复断裂、抓取抖动 | 迟滞+冷却+渐进三重抑制（§14.2）+ 人工 pause + L3 下冻结 |
| R4 | 接管雪崩（单点故障引发连锁过载） | 健康节点被压垮，故障扩散 | score 中 `recent_takeover_count` 惩罚项 + 容量准入 + WARMING + `max_concurrent_migrations` + catch-up 限流 |
| R5 | 灰故障静默漏采（TCP 通但抓取失败） | 该节点所有 slot 数据缺失却无人知晓 | 三层探测（§9.5），L-b 应用级健康 + L-c 金丝雀；抓取成功率纳入判定 |
| R6 | 中心控制面单点 | 全网区配置无法变更 | 控制面无状态多副本 + Leader 选举 + 四级降级阶梯（§3.2）+ LKG |
| R7 | 跨区共识集群多数派跨区部署 | 故障域全局化，任一区抖动拖垮全平台 | M1 红线（§6.2）：集群在中心侧，其他区只读 watch；实时决策不依赖跨区 |
| R8 | 时钟偏移导致租约/失效误判 | 提前抢占或延迟接管 | 强制 NTP + 权威时间源 + 最终以 token 裁决而非时间戳 |
| R9 | 未匹配网段静默错路由 | 实例被错区采集或完全漏采 | `UNKNOWN` 桶 + 强制人工告警（§4.2），禁止默认路由 |
| R10 | 维护标记遗忘 | 节点长期不参与调度，容量悄悄萎缩 | 标记强制 TTL + 责任人 + 到期提醒 + 容量水位告警 |
| R11 | 半截快照被当作有效 | 恢复出错误的采集范围，难排查 | 原子写入（tmp+fsync+rename）+ hash 校验 + 校验失败视为无快照（§7.2） |
| R12 | 重启节点不知道自己已被 fencing | 复活即大面积双主 | C 类自身状态快照 + 启动归属确认契约（§7.3 ②）+ 自我卸载契约 |
| R13 | 协议/广告格式不兼容 | 混合版本期探测失败、误判故障、配置无法解析 | 下发协议与**广告报文**双双向前兼容（§18.3）+ 版本门禁 + 混合版本专项测试 |
| R14 | 数据空洞被静默插值 | 运维基于假数据决策 | 展示层显式标注（§13.7）+ 实测空洞时长指标 |
| R15 | 区内最后一个节点被驱离 | 整区监控归零 | 显式护栏：拒绝驱离 + 告警（§12.3） |
| R16 | 2 节点区无法达成多数派 | 故障时无法自动接管 | §10.5：≥3 节点 / witness / 显式接受风险，三选一并在评审记录 |
| R17 | RDS 成为实时协调瓶颈 | 心跳/租约写入拖垮 DB | Collector/RC 不直连 DB（§6.4）+ 检测走 peer 互探 + DB 只承载低频期望态与审计 |
| R18 | remote-write 队列缓冲过短 | 崩溃时丢失超出预期的数据量 | 按可容忍空洞反推队列容量 + `oldest_sample_age` 告警（§13.6） |
| R19 | L3 长期滞留无人察觉 | 配置长期陈旧 → 新增实例静默漏采 | `degradation_level` + `manifest_age_seconds` 独立告警（§7.4、§19.1） |

## 21. 演进路线

一次性实现全部机制风险很高，建议按"先正确、再自治、后优化"推进：

**阶段 1 · 骨架与正确性**
- 中心 RDS：台账、网段映射、TaskSpec/RuleSpec 版本化、Zone Manifest 生成
- 跨区通道：M2 接口自检（digest 短路 + delta）为基线
- 内容/归属双通道分离（§8.2）+ 三类本地快照（§7）+ **启动归属确认契约**（§7.3）
- 固定加权 slot + **复合 token fencing**（§10.3）
- 节点状态机（含 SUSPECT / WARMING / QUARANTINED）
- 归属注册表（含历史区间）+ 基础查询接口
- 查询网关 + Zone Query Proxy 基础路由
> **验收**：`kill -9` 单节点，≤ 20 s 完成接管；被 kill 节点复活不产生双主；**中心控制面停机 30 min，各区采集与接管照常**（L1）；时点归属查询可答。

**阶段 2 · VRRP 式互探与自治**
- peer 互探（mesh/部分 mesh）+ 三层探测（含应用级健康）
- 观测矩阵上报 + 交叉验证 + `probe_untrusted` 识别
- 多数派投票 + 确定性 score 认领 + skew 让位
- 四级降级阶梯完整实现，重点打通 **L3 纯分布式自治**
- 分区处理（§10.4）与 2 节点区方案（§10.5）落地
- drain / quarantine / 缩容流程 + 审批审计 + 标记 TTL 治理
- 自监控指标全量接入（尤其 R1/R2/R12/R19 相关四项）
> **验收**：Coordinator 主备同时停机，区内仍能完成一次故障接管（L3）；模拟单向网络故障不引发误接管；模拟一个节点谎报"其他人都挂了"不引发接管风暴；滚动升级全程无 UNOWNED slot。

**阶段 3 · 连续性与优化**
- **相位对齐**（§13.2）+ **catch-up 抓取**（§13.3）+ 查询侧去重
- M3 长连接加速（M2 作为兜底保留）；或按需用 M1 替换
- 三重抑制的自动再均衡 + 目标函数调参
- `simulate` 预演能力
- 时点归属驱动的查询拼接优化（§17.1）
- 网区调整双写窗口流程（§18.4）
- 可选：连接预热（§13.4）、WAL 回填（§13.5）、中心长期存储
> **验收**：进程崩溃场景实测空洞 ≤ 1 个抓取周期且 catch-up 成功率 ≥ 99%；优雅驱离实测空洞 ≈ 0；扩缩容后 30 min 内负载偏差收敛到 ≤ 8%，迁移 slot 数不超过理论最小值 1.5 倍。

## 22. 评审时需要拍板的开放问题

1. **跨区连通模型选哪个**（§6.1）：M1 开放跨区 ZK/etcd / M2 接口自检 / M3 长连接 push。推荐 M2+M3 混合；若已有成熟跨区 ZK 运维体系可考虑 M1 替换 M3。**这条决定通道实现与安全评审范围，最先定。**
2. **网区数量与单区规模**：决定 §6.4 档位 A（etcd）还是档位 B（自研 Coordinator），以及 §9.2 探测拓扑（全连接 / 部分 mesh / 分组）。
3. **每区 collector 节点数是否 ≥ 3**：若存在 2 节点区，必须在 §10.5 三选项中选一个并记录为已接受风险。这直接决定自动接管能力。
4. **是否需要中心长期存储**：影响是否必须做样本级去重、`collector_id` 标签规范、带宽预算。与相位对齐（§13.2）的去重实现强相关。
5. **告警状态存哪里**：rc 接管时的告警去重方案取决于此（区内共享存储 vs 中心汇聚层去重）。
6. **抓取间隔与接管 SLO 的关系**：若 interval = 5 min，接管 SLO 20 s 已不是瓶颈，空洞主要由 interval 决定 → 应优先缩短关键 target 的 interval，而非继续优化接管速度。
7. **L3 自治的授权边界**：L3 下允许节点自主接管，是否需要人工审批开关？建议默认允许（否则违背要求 12 的初衷），但需配套最高级告警与事后审计。
8. **slot 总数定稿依据**：需上线前用真实 target 规模与序列基数压测确定（§5.3），事后变更代价极高。
9. **remote-write 队列缓冲时长**：等于崩溃场景的数据丢失上限（§13.6），需按业务可容忍空洞反推。
10. **是否启用连接预热**（§13.4）：收益与"变相双采"风险的权衡，建议阶段 3 再评估。
