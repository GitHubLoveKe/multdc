## 二、存储层架构设计

### 2.1 三种存储模式

用户在建设网区时可选择存储模式，这是网区级配置：

| 模式 | 形态 | 数据流 | 适用场景 |
|------|------|--------|---------|
| **模式 A：纯回写（Remote-Write Only）** | 网区无本地持久化 TSDB，采集器直接 remote-write 到中心/上级存储 | Collector → remote-write → 中心 VictoriaMetrics/Prometheus | 边缘站点、小区域、1 节点区；数据可容忍短暂中断 |
| **模式 B：本地 + 回写（Local + Remote-Write）** | 网区有本地 TSDB 做短期存储与查询，同时 remote-write 到中心长期存储 | Collector → 本地 TSDB（短期）+ remote-write → 中心（长期） | 大多数网区的默认选择；区内查询低延迟，跨区分析有中心汇聚 |
| **模式 C：本地 VM 集群 / 双机双写（Local VM Cluster / Dual-Node）** | 网区内部署 VictoriaMetrics 集群（或双节点互写），数据留在区内，可选是否回写中心 | Collector → 本地 VM 集群（主存储）→ 可选 remote-write → 中心 | 重保网区、大数据量网区、对数据主权/隔离有要求的场景 |

### 2.2 存储模式对现有架构的影响

存储模式的选择不是孤立的，它会**反向影响**协调层、查询层、数据连续性设计：

| 影响维度 | 模式 A（纯回写） | 模式 B（本地+回写） | 模式 C（本地 VM 集群） |
|---------|----------------|-------------------|---------------------|
| **区内查询** | ❌ 无法区内查询（无本地 TSDB），必须走中心 | ✅ 区内查询（短期）+ 中心查询（长期） | ✅ 区内查询（完整） |
| **Zone Query Proxy** | 不需要（无本地数据源） | 需要（聚合区内多个 Collector 的本地 TSDB） | 需要（查询 VM 集群端点） |
| **接管时数据连续性** | 依赖 remote-write 队列缓冲（队列满则丢数据） | 本地 TSDB 有 WAL 可回填 + RW 队列双保险 | VM 集群自身有副本，接管最平滑 |
| **中心不可达时** | 采集数据**全部丢失**（无法回写且无本地存储）→ 这是致命问题 | 本地 TSDB 暂存，恢复后补写 → 可接受 | 完全不受影响 → 最优 |
| **存储成本** | 最低（无区内存储） | 中（本地短期存储 + 中心长期存储，双份带宽） | 最高（区内完整存储集群） |
| **运维复杂度** | 低 | 中 | 高（区内多一个 VM 集群要运维） |
| **与 v0.2 设计的兼容性** | ⚠️ 需要大量调整（v0.2 假设每区有本地 TSDB） | ✅ 完全兼容 | ✅ 兼容，但 Zone Query Proxy 对接 VM 而非 Prometheus |
| **remote-write 队列缓冲要求** | 极高（队列 = 唯一数据保全手段） | 中（本地 TSDB 兜底） | 低（本地 VM 集群自身保全） |

### 2.3 时序库选型：Prometheus vs VictoriaMetrics

| 维度 | Prometheus TSDB | VictoriaMetrics (VM) |
|------|----------------|---------------------|
| **定位** | 原生 Prometheus 生态，标准 TSDB | 兼容 Prometheus 协议的高性能长期存储 |
| **性能** | 单节点约百万级活跃序列 | 单节点可承载千万级活跃序列，压缩率高 |
| **集群模式** | 无原生集群（需 Thanos/Cortex 补充） | 原生集群模式（vmstorage + vminsert + vmselect） |
| **双节点/HA** | 需 Thanos sidecar + 对象存储 或 Cortex | VM 集群天然支持多副本；双节点可用 vmstorage 2 副本 |
| **remote-write** | 原生支持 | 原生支持（且性能更好） |
| **查询兼容** | PromQL 原生 | PromQL 兼容（MetricsQL 超集） |
| **资源消耗** | 中 | 低（压缩效率高，同等数据量磁盘/内存更少） |
| **运维复杂度** | 低（单二进制） | 中（集群模式多组件）；单二进制版本也很简单 |
| **与 vmagent 的协同** | 可用但非最佳搭配 | 天然搭配（同一生态，协议一致） |
| **长期存储** | 需外部方案（Thanos 接对象存储等） | 原生支持长期存储 |

**关键判断**：

如果选择 VictoriaMetrics 作为时序库，那么：
- vmagent 作为采集器就是**天然搭配**（同一生态、协议一致、配置可复用）
- 模式 C（本地 VM 集群）的实现成本大幅降低
- 模式 B 的中心存储也用 VM，查询侧统一 PromQL/MetricsQL
- 模式 A 的中心存储用 VM，区内无存储

如果选择 Prometheus 作为时序库，那么：
- vmagent 仍然可以用（vmagent 支持 remote-write 到 Prometheus），但不是"原生搭配"
- 模式 C 需要 Thanos 或类似方案来实现集群/HA，复杂度上升
- 模式 B 的中心长期存储需要额外方案（Prometheus 本身不适合做长期存储）

**建议**：如果存储模式要支持模式 C（本地 VM 集群），**VictoriaMetrics 是更一致的选择**，因为它与 vmagent 同生态、原生支持集群、且长期存储能力远优于 Prometheus 原生 TSDB。

### 2.4 模式 C 详细设计：双节点 / VM 集群

用户提到"本地 vm 集群/双机双写（双节点模式）"，这里有两个子方案：

**子方案 C1：VictoriaMetrics 集群（推荐）**

```
网区内部署：
  vminsert (×1~2) ← Collector/vmagent 写入入口
  vmstorage (×2)  ← 数据存储，2 副本
  vmselect (×1~2) ← 查询入口

  Collector/vmagent → vminsert → vmstorage (2 副本)
  Zone Query Proxy → vmselect → 返回结果

优点：原生集群、自动副本、查询自动去重、扩容方便
代价：多组件部署（但 VM 单二进制也可以跑 cluster 模式）
```

**子方案 C2：双机双写（简化版）**

```
网区内部署两个独立 VM/Prometheus 实例：
  VM-Primary ← Collector 写入
  VM-Secondary ← Collector 同时写入（双写）

  Collector 配置两个 remote-write 端点，同一份数据写两份
  Zone Query Proxy 查询时选其一（或对比取最新）

优点：极简，无集群组件
缺点：双写带宽翻倍；无自动去重；查询侧需自行处理重复数据；
      两个实例各自独立，没有副本一致性保证
```

**建议**：C1（VM 集群）优于 C2（双写），因为 C2 的"双写"本质上是在应用层模拟副本，而 VM 集群的副本机制更成熟、更高效。C2 唯一优势是"不需要学 VM 集群部署"，但如果已经选了 VM，集群部署并不复杂。

### 2.5 存储模式与 v0.2 设计的冲突点

| 冲突 | 说明 | 建议处理 |
|------|------|---------|
| **v0.2 假设每区有本地 TSDB** | v0.2 的 Zone Query Proxy、WAL 回填、本地查询等设计都假设区内有 TSDB。模式 A 无本地 TSDB，这些设计全部失效 | 模式 A 需要单独设计查询路径（直接查中心）和连续性保障（RW 队列 + 可选 host agent 兜底） |
| **remote-write 去重标签** | v0.2 取舍 4 提到需要 `collector_id` / `__replica__` 标签去重。模式 B/C 下中心存储会收到多份数据，去重规则需要与存储模式联动 | 统一标签规范：`(collector_id, zone_id, __replica__)` 作为去重键，无论哪种存储模式都打 |
| **WAL 回填的前提条件** | v0.2 §13.5 的 WAL 回填假设"节点间磁盘可访问"。模式 A 下无本地 TSDB，WAL 回填不适用 | 模式 A 明确标注"WAL 回填不可用"，连续性依赖 RW 队列缓冲 |
| **Zone Query Proxy 的实现** | 模式 A 无区内数据源，Proxy 无意义；模式 B Proxy 聚合多 Collector 本地 TSDB；模式 C Proxy 对接 VM 集群 | Proxy 按存储模式分支实现：A=不部署 / B=聚合 Prometheus 端点 / C=对接 vmselect |

## 三、采集器架构设计

### 3.1 两种采集器架构

| 架构 | 形态 | 说明 |
|------|------|------|
| **架构 X：vmagent 模式** | 使用 VictoriaMetrics 的 vmagent 作为统一采集器 | vmagent 原生支持 Prometheus scrape、remote-write、多种采集协议；配置兼容 Prometheus scrape_config；单二进制部署 |
| **架构 Y：job + agent 分离模式** | job（调度/编排）与 agent（执行/采集）分离，job 维护任务调度，agent 维护采集能力 | job 负责"采什么、什么时候采、写到哪"；agent 负责"怎么采"（各种协议的具体实现）；job 调用 agent 执行采集任务 |

### 3.2 架构 X：vmagent 模式详细分析

```
┌─────────────────────────────────────────────────┐
│ 网区                                            │
│                                                  │
│  vmagent-1 ←── 配置 ── Zone Agent/Coordinator   │
│  vmagent-2 ←── 配置 ── Zone Agent/Coordinator   │
│  vmagent-3 ←── 配置 ── Zone Agent/Coordinator   │
│                                                  │
│  每个 vmagent：                                   │
│    · 持有区内完整 scrape 配置（= Zone Manifest    │
│      转换为 vmagent 格式的 scrape_configs）        │
│    · 执行抓取 → 写入本地 TSDB 或 remote-write     │
│    · 支持 Prometheus 协议的各种 exporter           │
│                                                  │
│  优点：                                           │
│    · 单二进制，部署简单                             │
│    · 与 VictoriaMetrics 生态天然兼容                │
│    · 原生 remote-write，性能优秀                    │
│    · 配置格式兼容 Prometheus，迁移成本低             │
│    · 内置服务发现（file_sd, consul, dns 等）        │
│                                                  │
│  局限：                                           │
│    · 采集协议以 Prometheus scrape 为主              │
│    · SNMP/JMX/custom protocol 需要 exporter 转换   │
│    · 非 scrape 类采集（如拨测、端口扫描）需要扩展     │
│    · vmagent 是"黑盒"组件，深度定制需要改源码        │
└─────────────────────────────────────────────────┘
```

### 3.3 架构 Y：job + agent 分离模式详细分析

```
┌──────────────────────────────────────────────────────────────┐
│ 网区                                                          │
│                                                               │
│  ┌──────────────────────┐                                     │
│  │ Job Scheduler        │  ← 区内 Coordinator 下发任务编排     │
│  │ · 维护任务列表        │                                     │

│  │ · 管理采集周期        │                                     │
│  │ · 归属管理（slot）    │                                     │
│  └──────────┬───────────┘                                     │
│             │ 调用（gRPC/HTTP/本地 IPC）                        │
│             ▼                                                  │
│  ┌──────────────────────┐  ┌──────────────────────┐           │
│  │ Agent Type A         │  │ Agent Type B         │           │
│  │ (Prometheus scrape)  │  │ (SNMP/JMX/Custom)    │           │
│  │ · HTTP/HTTPS scrape  │  │ · SNMP walk           │           │

│  │ · 指标标准化         │  │ · 自定义协议            │           │
│  └──────────────────────┘  └──────────────────────┘           │

│  │ · TCP/UDP 拨测       │  │ · ...                  │           │
│  │ · HTTP 拨测          │  │                        │           │
│  │ · ICMP               │  │                        │           │
│  └──────────────────────┘  └──────────────────────┘           │
│                                                               │
│  数据流：                                                      │
│    Job 调度 → 调用对应 Agent → Agent 执行采集 → 结果回传 Job    │
│    → Job 统一格式化 → 写入时序库（本地 TSDB / remote-write）    │
│                                                               │
│  优点：                                                        │
│    · 采集类型可扩展（新增 Agent Type 即可）                      │
│    · Job 与 Agent 独立演进、独立升级                             │
│    · Job 统一管理数据写入，Agent 只关心采集                      │

│                                                               │
│  局限：                                                        │
│    · 架构复杂度高（多进程/多组件）                                │
│    · Job ↔ Agent 通信需要设计协议                                │
│    · Agent 注册/发现/健康检查需要额外实现                         │
│    · 数据从 Agent 回传到 Job 有额外开销                          │
└──────────────────────────────────────────────────────────────┘
```

### 3.4 两种架构对比

| 维度 | X: vmagent 模式 | Y: job+agent 分离模式 |
|------|----------------|---------------------|
| 部署复杂度 | 低（单二进制） | 高（多组件） |
| 采集类型扩展性 | 中（依赖 exporter 生态） | 高（新增 Agent Type） |
| 与 VM 生态兼容性 | 最佳 | 需适配 |
| 与 v0.2 架构融合 | 中（vmagent 替代 Collector 角色，slot/归属机制需适配） | 高（Job ≈ Collector + Coordinator 的调度部分，Agent ≈ 执行器） |
| 配置管理 | vmagent 原生 file_sd / http_sd | Job 维护，Agent 按需获取 |
| 故障隔离 | 单 vmagent 故障 = 该节点所有采集停 | Agent 故障只影响特定采集类型 |
| 运维成本 | 低 | 高 |
| 团队熟悉度 | 如果团队熟悉 Prometheus 生态则高 | 需要自研，学习成本 |
| 适合场景 | 以 Prometheus scrape 为主的标准化监控 | 多协议、多采集类型的混合监控 |

### 3.5 混合架构（推荐考虑）

实际上可以走一条中间路线：

```
┌───────────────────────────────────────────────────────┐
│ 网区                                                   │
│                                                        │
│  vmagent（主采集器）                                    │
│    · 承担标准 Prometheus scrape 任务（绝大多数场景）     │
│    · 持有 Zone Manifest（转换为 scrape_configs）        │
│    · remote-write 到本地 TSDB / 中心                   │
│                                                        │
│  + 专用 Agent（补充采集器，按需部署）                    │
│    · SNMP Agent：处理 SNMP 设备采集                    │
│    · Probe Agent：处理拨测/端口探测                     │
│    · Custom Agent：处理特殊协议                         │
│                                                        │
│  专用 Agent 的数据写入路径：                             │
│    方案 a：Agent → remote-write → 时序库（独立写入）     │
│    方案 b：Agent → 标准 exporter 协议 → vmagent 抓取    │
│             （Agent 暴露 metrics 端点，vmagent 来 scrape）│
│    方案 c：Agent → 本地文件 → vmagent 读取              │
│             （Agent 写文件，vmagent 用 file_sd 读取）    │
│                                                        │
│  优点：                                                 │
│    · 主力采集用 vmagent（简单、成熟、高性能）             │
│    · 特殊采集用专用 Agent（灵活、可扩展）                 │
│    · 方案 b 最优雅：Agent 只需暴露 /metrics 端点，       │
│      vmagent 统一 scrape，数据流与标准采集完全一致        │
└───────────────────────────────────────────────────────┘
```

**方案 b 的巧妙之处**：专用 Agent 不需要自己实现 remote-write、不需要知道存储在哪里、不需要参与 slot 归属——它只需要把自己采集的数据以 Prometheus 指标格式暴露在一个 HTTP 端点上，vmagent 像 scrape 任何 exporter 一样去抓它。这把"多采集类型"问题转化为了"多 exporter"问题，完全在 vmagent 生态内闭环。

## 四、凭据安全设计（C3 详细展开）

### 4.1 问题域

采集器在抓取目标时需要各种凭据：
- HTTP Basic Auth 的用户名/密码
- SNMP community string / v3 认证信息
- TLS 证书 / 客户端证书
- SSH 密钥（SSH exporter 场景）
- 数据库连接凭据
- API Token / Bearer Token
- 云服务 AK/SK

### 4.2 凭据放在哪里的三种模型

| 模型 | 形态 | 安全性 | 复杂度 | 适用 |
|------|------|--------|--------|------|
| **模型 1：凭据放在 Job 参数中** | 中心控制面在生成 Zone Manifest 时，将凭据明文/加密后嵌入任务配置 | 低~中（凭据随配置传播到每个 Collector） | 低 | 安全要求不高的内网环境 |
| **模型 2：Agent 运行时获取凭据** | Job 参数中只包含凭据引用（credential_id），Agent 执行采集时向凭据服务请求实际凭据 | 高（凭据不随配置传播，只在执行时按需获取） | 中~高 | 安全要求高的场景 |
| **模型 3：凭据代理层（Credential Vault）** | 区内部署凭据代理（如 Vault Agent / 自研凭据缓存），Agent 从本地代理获取凭据 | 最高（凭据有 TTL、自动轮转、审计） | 高 | 企业级安全要求 |

### 4.3 凭据传输安全

无论哪种模型，凭据在传输中必须加密：

```
凭据生命周期：
  ① 录入：用户在中心控制面录入凭据 → 加密存储（AES-256 / Vault）
  ② 下发：
     - 模型 1：中心 → 跨区通道（M2/M3）→ Zone Manifest 中包含加密凭据
              → Collector 解密后使用（密钥从哪来？→ 需要密钥分发机制）
     - 模型 2：中心 → 跨区通道 → Zone Manifest 中只有 credential_id
              → Agent 向凭据 API 请求 → 凭据 API 验证 Agent 身份 → 下发凭据
     - 模型 3：中心 → 凭据同步到区内 Vault → Agent 从 Vault 读取
  ③ 使用：Agent 在内存中持有明文凭据用于采集，不落盘
  ④ 轮转：凭据过期 → 中心触发轮转 → 通知各区更新 → Agent 获取新凭据
  ⑤ 审计：凭据访问记录留痕
```

### 4.4 凭据方案与采集器架构的关系

| 采集器架构 | 适配的凭据模型 | 说明 |
|-----------|--------------|------|
| vmagent 模式 | 模型 1 为主 | vmagent 的 scrape_config 直接包含凭据（basic_auth, bearer_token 等），通过 file_sd + 加密配置文件下发 |
| job+agent 分离 | 模型 2 为主 | Job 参数中只含 credential_id，Agent 运行时向凭据服务获取 |
| 混合架构 | 模型 1 + 2 混合 | vmagent 用模型 1（配置文件含凭据），专用 Agent 用模型 2（按需获取） |

## 六、超出当前框架的补充思考

### 6.1 采集器架构对 v0.2 "Collector" 概念的重构

v0.2 的 Collector 是一个"全功能"组件：持有 Manifest、参与互探、执行采集、写入 TSDB。引入 vmagent / job+agent 后，Collector 的角色需要拆分：

```
v0.2 Collector（全功能）
    ↓ 拆分为
┌─────────────────────────────────────────────┐
│ 调度面（Scheduler / Sidecar）                │ ← 保留 v0.2 的所有调度逻辑
│  · 持有 Zone Manifest                        │
│  · 参与 peer 互探、slot 归属                 │
│  · 管理本地 Agent/vmagent 的生命周期          │
│  · 上报状态、接收归属变更                     │
├─────────────────────────────────────────────┤
│ 执行面（vmagent / Agent）                    │ ← 纯采集，不参与调度
│  · 执行抓取/探测                             │
│  · 格式化指标                                │
│  · 写入时序库或回传 Scheduler                │
└─────────────────────────────────────────────┘
```

这个拆分与 v0.2 的"集中管理、分散执行"理念一致：**调度面负责"分散执行"中的协调部分，执行面负责纯采集**。v0.2 的所有 peer 互探、归属裁决、epoch fencing 逻辑都在调度面，执行面对此完全无感知。

**收益**：
- 执行面可以独立升级（新增采集类型不需要改调度逻辑）
- 调度面可以复用（不同类型的执行面共享同一套调度框架）
- 故障隔离：vmagent 崩溃不影响调度面，调度面可以重启 vmagent 或切换到备用 Agent

### 6.2 存储模式选择对容量规划的影响

不同存储模式对网区的硬件规划差异很大：

| 资源 | 模式 A | 模式 B | 模式 C |
|------|--------|--------|--------|
| 区内磁盘 | 无特殊要求 | 需 TSDB 磁盘（按活跃序列 × 保留期计算） | 需 VM 集群磁盘（更大，但压缩率高） |
| 区内内存 | 无特殊要求 | 需 TSDB 内存（按活跃序列数计算） | 需 VM 内存 |
| 跨区带宽 | 高（全量数据 remote-write） | 中（全量 RW + 区内本地） | 低~无（可选回写） |
| 中心存储 | 大（汇聚所有区的数据） | 大（同上） | 小（只收模式 A/B 区的回写） |

### 6.3 采集器凭据的"最小权限"原则

无论选哪种凭据模型，建议遵循：
- 每个采集任务只获取自己需要的凭据（不是整个区的凭据）
- 凭据有 TTL，到期自动轮转
- 凭据访问有审计日志
- 凭据不在日志/指标/错误信息中泄露（脱敏处理）

### 6.4 是否需要考虑"采集器即服务"（CaaS）模式

当前设计假设采集器部署在网区内的物理/虚拟机上。如果未来有容器化部署的可能（K8s 集群内），采集器的部署模式会变化：
- vmagent 可以作为 DaemonSet 或 Deployment 部署
- slot 归属可以从"节点级"变为"Pod 级"
- peer 互探可以利用 K8s Service Discovery

这不阻塞当前设计，但建议在架构中预留"采集器注册时声明部署模式"的扩展点。
