### 1.2 数据流总览

```
【任务下发流】
中心控制面 → selector 展开 → Zone Manifest 生成
→ 跨区通道（M2/M3）→ Zone Agent 接收
→ 区内广播 → 所有 Job Scheduler 持有完整 Manifest

【任务路由（写路径）】
任务根据网段规划（默认）或用户选取的网区执行
→ 中心确定目标 zone → 下发 Zone Manifest
→ Job Scheduler 接收 → 按 slot 归属调度 Agent 执行采集
→ Agent 采集数据 → 写入 OTel Collector
→ OTel Collector 按存储模式路由输出（原生多写 + 负载均衡）：
    模式 A：remote-write → 中心 VictoriaMetrics
    模式 B：本地 VM 写入 + remote-write → 中心 VM
    模式 C：本地 VM 集群写入（+ 可选 remote-write）

【读取路由（读路径）——与任务路由分离】
读取根据实例所在网区的存储模式智能路由：
  · 中心有数据（模式 A/B/C 均有 remote-write）→ 查中心 VM
  · 仅本地有数据（极端场景：模式 A + 中心不可达）→ 不可查
  · 本地有完整数据（模式 B/C）→ 优先查本地 Zone Query Proxy
用户查询 → Grafana / 中心查询网关 → 解析 instance+zone 标签
→ 查询网关根据该 zone 的存储模式决定路由策略：
    模式 A：直接查中心 VM（无 Zone Query Proxy）
    模式 B：fan-out → Zone Query Proxy 聚合区内本地 VM
    模式 C：fan-out → Zone Query Proxy 对接 vmselect
→ 返回 → 网关 merge → Grafana 展示
跨区混合查询（如拨测）：多 zone 数据 fan-out → merge → 混合计算展示

【归属协商流】
Coordinator 签发 slot 归属 → watch 推送（L0/L1/L2）
或 peer 互探广告携带归属摘要（L3）
→ 各 Job Scheduler 按归属调度 Agent 执行

【心跳/检测流】
Job Scheduler ↔ Job Scheduler：VRRP 式 peer 互探（3s 周期）
Job Scheduler ↔ Coordinator：存活 session（15s 心跳）
Job Scheduler → 中心：观测矩阵上报（10s 周期）

【告警流】
RC 区内本地取数（仅模式 B/C 区部署）→ 规则评估 → 告警产生 → 中心告警汇聚
模式 A 区无 RC，告警由中心基于 remote-write 到中心 VM 的数据评估
```

### 1.3 四级降级阶梯

| 级别 | 触发 | 权威 | 可用能力 | 冻结能力 |
|------|------|------|---------|---------|
| L0 正常 | 全部可用 | 中心 + Coordinator + peer | 全部 | — |
| L1 中心不可达 | 跨区中断 | 区内 Coordinator | 采集/检测/接管/驱离/再均衡 | 任务定义变更 |
| L2 Coordinator 主不可用 | 主节点故障 | 备节点 | 同 L1 | 同 L1 + 切换期暂停迁移 |
| L3 协调器全失 | 主备皆失 | Job Scheduler 集群（纯分布式） | 采集/检测/多数派接管 | 再均衡/配置变更 |

### 1.4 网区规模适配

| 规模 | 节点数 | HA 模式 | quorum | 自动接管 |
|------|--------|---------|--------|---------|
| 小区域 | 1 | none | 1 | 无（单点故障=全区停摆） |
| 普通网区 | 2 | coordinator_assist / asymmetric / witness | 2 | 需额外机制（见分区方案） |
| 重保网区 | ≥3 | standard VRRP | ≥2 | 标准自治 |

## 二、核心设计决策汇总

### 2.1 已确定的设计原则

| # | 原则 | 含义 | 来源 |
|---|------|------|------|
| P1 | 集中管理 ≠ 集中调度 | 中心是唯一定义权威，但不是实时裁决权威 | v0.2 取舍 1 |
| P2 | 任务内容与归属解耦 | 全区 Manifest 广播，归属只是轻量映射 | v0.2 取舍 2 |
| P3 | 检测权分布式化 | VRRP 式 peer 互探，中心只做观测与仲裁 | v0.2 取舍 3 |
| P4 | at-least-once，允许短暂双采 | 接管允许 ≤1 抓取周期重叠 | v0.2 取舍 4 |
| P5 | 无多数派时选空洞不选双主 | 无法达成共识时宁可停采也不双主 | v0.2 取舍 6 |
| P6 | 迁移有成本，要"懒" | 再均衡带迟滞+冷却+渐进三重抑制 | v0.2 取舍 7 |
| P7 | 去除加权（当前阶段） | slot 均等分配，后续可迭代加权 | v2 需求变更 |
| P8 | 任务路由与读取路由分离 | 任务按网段规划路由到目标 zone；读取按该 zone 的存储模式智能路由到数据所在地 | 架构决策 |
| P9 | OTel Collector 是统一数据管道 | OpenTelemetry Collector 替代自研 Collector，不采集、不调度，专注多输入多输出的数据路由与转发，原生支持多写/负载均衡/插件扩展 | v3 架构决策 |
| P10 | 网区内 job+agent 分离 | Job Scheduler 负责调度协调，Agent 负责采集执行，职责清晰分离 | 架构决策 |
| P11 | RC 与存储绑定 | RC 仅部署在有本地存储的网区（模式 B/C），纯回写区（模式 A）不部署 RC；RC 取数策略与查询路由一致（优先本地） | v3 架构决策 |
| P12 | 时序存储优先 VictoriaMetrics | 全链路优先 VM（区内 + 中心），OTel Collector 通过 exporter 配置适配多组件 | v3 架构决策 |
| P13 | 存储与采集分离、任务与采集器分离 | 存储层独立于采集层演进；任务定义（Manifest）与采集执行器（Agent）解耦 | v3 强化 |

## 三、文档间冲突清单

### 3.1 架构级冲突（不同文档之间的设计矛盾）

| # | 冲突 | 详细说明 | 涉及文档 | 建议处理 |
|---|------|---------|---------|---------|
| **C1** | **模式 A 与 v0.2 核心假设根本冲突** | v0.2 几乎所有设计都假设区内有本地 TSDB：Zone Query Proxy 聚合区内数据源（§17）、WAL 回填（§13.5）、本地查询（§11.2）、数据连续性预算（§13.1）。模式 A 无本地 TSDB，这些设计全部失效。 | v0.2 vs v3 | 模式 A 应定位为"非标准模式"，仅用于 1 节点区/边缘站点。需显式标注：① 不部署 Zone Query Proxy；② 连续性预算中明确"中心不可达时数据全丢"；③ remote-write 队列缓冲时长 = 可容忍最大空洞 |
| ~~**C2**~~ | ~~vmagent 与 v0.2 Collector 角色映射不清~~ | ~~v0.2 Collector 全功能 vs vmagent 纯采集~~ | ~~v0.2 vs v3~~ | ✅ 已解决：引入 Collector 作为统一数据管道，Job Scheduler 承担调度职责，Agent 承担采集职责，三者职责清晰分离。v0.2 的 Collector 概念拆分为 Job Scheduler + Collector(数据管道) |
| **C3** | **加权 vs 均等分配的历史遗留矛盾** | v0.2 取舍 5 明确写"slot 必须按权重分配"，v2 去除了加权改为均等。但 v3 又提出"异构 Agent 部署"场景（节点 A 有 SNMP Agent，节点 B 没有），均等分配在此场景下失效。 | v0.2 vs v2 vs v3 | 建议：当前阶段均等分配 + 能力约束感知（在满足能力前提下的均等），本质是加权的轻量变种。后续正式引入加权时需回写 v0.2 取舍 5 |
| **C4** | **存储模式可选与统一标签规范的张力** | v0.2 取舍 4 要求统一的 `collector_id` / `__replica__` 标签去重。但三种存储模式到中心的数据流不同：模式 A 只一份、模式 B 双份、模式 C 可选回写。去重规则需要适配不同模式。 | v0.2 vs v3 | 统一采集侧标签 `(zone_id, collector_id, slot_id)`，中心按存储模式决定去重策略：A=不去重；B=按 (series,timestamp) 去重；C=按 zone_id 区分 |
| ~~**C5**~~ | ~~job+agent 模式下 slot 归属对象不明确~~ | ~~slot 归属 Job 还是 Agent~~ | ~~v0.2 vs v3~~ | ✅ 已解决：slot 归属 Job Scheduler（≈ v0.2 的 Collector），Agent 只是执行器。Agent 故障不影响归属，Job Scheduler 重新分配 Agent 即可 |
| **C6** | **v0.2 的"全区广播"与凭据安全的矛盾** | v0.2 取舍 2 要求全区 Manifest 广播到所有 Collector。但如果 Manifest 包含凭据（模型 1），则凭据扩散到每个节点；如果用模型 2（运行时获取），则 Manifest 中只有 credential_id，与"全区持有完整清单"有微妙冲突。 | v0.2 vs v3 | 建议：Manifest 中不含凭据，只含 credential_id 引用。凭据通过独立通道（凭据 API / Vault）按需获取。这与"内容广播"不矛盾——广播的是任务定义，凭据是执行时资源 |

### 3.3 新架构引入的待解决问题（v2 新增）

| # | 问题 | 详细说明 | 建议处理 |
|---|------|---------|---------|
| **C11** | **Job Scheduler → Agent 调度协议未定义** | Job Scheduler 如何调用 Agent 获取数据？是 push 模式（Scheduler 主动拉取 Agent 数据）还是 pull 模式（Scheduler 下发任务，Agent 主动推送结果）？协议选型（HTTP/gRPC/消息队列）影响延迟、可靠性和扩展性。 | 建议：Scheduler → Agent 采用 push 模式（Scheduler 按 scrape interval 调用 Agent），Agent 返回采集数据。协议建议 HTTP（与 Prometheus 生态一致）或 gRPC（高性能场景） |
| **C12** | **Agent → OTel Collector 数据写入协议** | Agent 采集的数据如何写入 OTel Collector？OTel 原生支持 OTLP 协议，但 Prometheus 采集场景通常使用 remote-write 或直接暴露 metrics 端点。需要确定 Agent 与 OTel Collector 之间的协议。 | 建议：Agent 通过 OTLP 协议 push 到 OTel Collector（OTel 原生支持），或 Agent 暴露 metrics 端点由 OTel Collector 的 prometheus receiver 拉取。前者更适合 push 模型 |
| **C13** | **OTel Collector 输出路由配置管理** | OTel Collector 如何根据存储模式配置不同的 exporter？是静态配置文件（otel-collector-config.yaml）还是动态下发（中心控制面推送）？多路输出时 OTel 原生支持 load balancing exporter。 | 建议：启动时根据 zone 存储模式生成 OTel 配置，支持多 exporter 同时输出。模式切换时重新生成配置并热加载。OTel 原生 loadbalancing exporter 可处理多 VM 实例场景 |
| **C14** | **OTel Collector 部署粒度** | OTel Collector 是每节点一个（与 Job Scheduler 同机）还是全区共享一个（独立集群）？每节点一个更简单但可能有资源冗余；全区共享更灵活但引入额外网络跳数和单点风险。 | 建议：每节点一个 OTel Collector（与 Job Scheduler 同机部署），简单可靠。OTel Collector 资源占用低，每节点部署可避免额外网络依赖。后续如有需要可演进为 Collector 集群 |
| **C15** | **Agent 故障时的任务重分配** | Agent 故障时，Job Scheduler 是否需要重新分配该 Agent 负责的 slot？还是等待 Agent 恢复？如果 Agent 长时间不恢复，是否需要启动备用 Agent？ | 建议：Agent 故障不影响 slot 归属（slot 归属 Job Scheduler）。Scheduler 检测到 Agent 故障后，将受影响 slot 的采集任务重新分配给其他可用 Agent（同节点或跨节点） |

### 5.1 v0.2 概念 → 实际组件映射（v3 更新）

| v0.2 概念 | 实际组件 | 说明 |
|-----------|---------|------|
| Collector（全功能） | **Job Scheduler** + **OTel Collector** + **Agent** | v0.2 的 Collector 拆分为三个独立组件，数据管道采用 OpenTelemetry Collector |

| Zone Coordinator | etcd 集群 / 自研双节点 | 按网区规模选型 |

| RC | 独立组件，同构互探，**与存储绑定** | 仅部署在模式 B/C 区，模式 A 区不部署 |
| Zone Query Proxy | 按存储模式分支实现 | A=不部署 / B=聚合区内本地 VM / C=对接 vmselect |
| 展示层 | **Grafana**（前期） | 多数据源管理、跨区查询、动态 instance→zone 路由 |

```
│  │    · 标签注入（zone_id, collector_id, slot_id）                    │  │
│  │    · 数据格式化、过滤、批处理                                       │  │
│  │                                                                 │  │
│  │  输出端（OTel exporter，按存储模式配置，可多路同时）：                 │  │
│  │    ┌─────────────────┐  ┌──────────────┐  ┌──────────────┐     │  │
│  │    │ remote-write    │  │ 本地 VM      │  │ 本地 VM 集群 │     │  │
│  │    │ → 中心 VM       │  │ 写入         │  │ 写入         │     │  │
│  │    │ (所有模式)       │  │ (模式 B)     │  │ (模式 C)     │     │  │
│  │    └─────────────────┘  └──────────────┘  └──────────────┘     │  │
│  │                                                                 │  │
│  │  原生能力：多写 + 负载均衡 + batching + retry + 插件生态             │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                       │

│  │  · 模式 A 区不部署（告警由中心统一评估）                             │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

**关键设计收益（v3 更新）**：

1. **职责清晰**：Job Scheduler 只管调度，Agent 只管采集，OTel Collector 只管数据路由——三者可独立演进
2. **OTel 生态加持**：无需自研数据管道，OTel Collector 原生提供多写、负载均衡、batching、retry、插件扩展
3. **全链路 VM**：区内 + 中心统一 VictoriaMetrics，OTel 通过 exporter 配置适配，技术栈一致
4. **RC 与存储绑定**：RC 仅在有本地数据的区部署，避免无意义的跨区取数；模式 A 区告警由中心统一处理
5. **Agent 极简**：Agent 不需要知道存储在哪里、不需要实现 remote-write、不需要参与 slot 归属——它只采集数据并返回
6. **扩展性强**：新增采集类型只需加一种 Agent；新增输出目标只需加一个 OTel exporter（日志、消息队列等）

### 5.3 存储模式与查询路径（v3 更新）

| 存储模式 | 区内查询 | 跨区查询 | RC 部署 | 中心不可达时 |
|---------|---------|---------|---------|-------------|
| A（纯回写） | 不支持（无本地数据） | 查中心 VM | **不部署** | 数据全丢 + 无告警 |
| B（本地+回写） | Zone Query Proxy 聚合区内本地 VM | 中心网关 fan-out | **部署** | 区内查询+告警可用 |
| C（本地 VM 集群） | Zone Query Proxy 对接 vmselect | 中心网关 fan-out | **部署** | 区内查询+告警可用（最优） |

### 5.4 任务路由与读取路由分离（v3 更新）

**核心思想**：任务往哪里写 和 用户从哪里读 是两条独立的路径，各自有自己的路由逻辑。

```
【任务路由（写路径）】
  决策依据：网段规划（默认）或用户选取的网区
  路由逻辑：中心 → 确定目标 zone → 下发 Zone Manifest → Job Scheduler 执行
  数据终点：由 OTel Collector 按该 zone 的存储模式决定输出目标（VM）

【读取路由（读路径）】
  决策依据：实例所在 zone 的存储模式
  路由逻辑：Grafana / 查询网关 → 解析 instance+zone 标签 → 查 zone 存储模式 → 智能路由
    · 模式 A：直接查中心 VM（数据只存在于中心）
    · 模式 B：fan-out → Zone Query Proxy 聚合区内本地 VM + 中心 VM merge
    · 模式 C：fan-out → Zone Query Proxy 对接 vmselect（本地数据最完整）

【RC 路由（与读取路由一致）】
  决策依据：zone 存储模式（RC 与存储绑定）
  路由逻辑：
    · 模式 A：无 RC，告警由中心基于中心 VM 数据评估
    · 模式 B/C：RC 优先查区内本地 VM，降低延迟和网络开销

【跨区混合查询（如拨测）】
  决策依据：拨测任务跨多个 zone，数据分散在各区 VM 中
  路由逻辑：中心查询网关 fan-out → 多 zone VM 数据 → merge → 混合计算 → Grafana 展示
  关键能力：需要 instance+zone 标签定位数据所在区，支持多区数据聚合

【分离的收益】
  1. 任务下发不需要关心数据存在哪里——只管写到 OTel Collector，Collector 负责路由
  2. 查询不需要关心任务是怎么下发的——只管按存储模式找到数据所在地
  3. RC 部署不需要关心任务怎么分发——只管跟随存储，有本地数据就有 RC
  4. 存储模式切换时，任务路由逻辑不变，只有读取路由、RC 路由和 OTel 输出需要适配
```

### 5.5 Grafana 展示层与多数据源策略（v3 新增）

**定位**：前期使用 Grafana 作为指标展示层，需要解决数据源管理、跨区查询、动态路由三个核心问题。

```
【数据源维护策略】
  阶段 1（推荐）：Grafana 只配置"中心查询网关"作为唯一数据源
    · 优点：简单，Grafana 无需感知多 zone 存在
    · 缺点：所有查询经过网关，延迟略高
    · 数据源可用性由网关层屏蔽，Grafana 无需自动维护

  阶段 2（可选）：增加区内直连数据源
    · 每个 zone 的 Zone Query Proxy 作为独立数据源
    · 需要 Grafana 数据源自动维护插件（对接 zone registry）
    · 优点：区内查询延迟低；缺点：数据源管理复杂度上升

【跨区查询实现】
  中心查询网关提供统一 PromQL 接口：
    · 接收 Grafana 查询请求
    · 解析 instance+zone 标签，确定数据所在 zone 列表
    · fan-out 到各 zone 的 VM / Zone Query Proxy
    · merge 结果后返回 Grafana
  Grafana 侧无需特殊配置，只需对接网关一个数据源

【动态 instance → zone 路由】
  中心维护 instance → zone 映射表（实例台账的一部分）：
    · 查询网关根据 instance 标签查映射表
    · 单 zone 数据：直接路由到该 zone
    · 多 zone 数据（如拨测）：fan-out 到所有相关 zone
    · 映射表由中心控制面维护，Zone Agent 上报区内实例清单

【混合计算与展示（如拨测）】
  拨测数据特点：同一拨测任务可能在多个 zone 执行，数据分散在各区 VM
  实现方案：
    · 中心网关 fan-out → 多 zone VM 查询 → merge → 混合计算（成功率、延迟分布等）
    · Grafana 侧使用混合查询面板展示多区结果
    · 标签规范：拨测数据需携带 zone_id 标签，便于网关路由和结果区分
```
