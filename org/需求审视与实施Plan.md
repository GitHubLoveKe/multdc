1. **调度模式的方案横向对比**：用户明确要求"列出方案对比，不局限于我的设想"，v0.2 直接给出了最终方案（VRRP式 + 声明式），但缺少与其他候选方案的显式对比论证
2. **任务类型差异化策略**：普通任务（主机/数据库）和探测任务（端口/拨测）的网区分配策略需要显式区分

## 二、补充设计：三个缺口

### 2.1 调度模式方案对比（补充 §1.2 的决策论证）

v0.2 最终选择了"声明式期望态 + 区内 VRRP 自治"，但用户要求看到多方案对比。以下补充调度维度的候选方案：

| 方案 | 核心思路 | 平台角色 | 区内角色 | 与 v0.2 关系 |
|------|---------|---------|---------|-------------|
| **A. 平台集中调度** | 平台计算 task→Worker 分配，下发到区 | 实时调度器 | 被动执行 | ❌ 违背"平台管到区"诉求，且跨区实时调度不可靠（v0.2 取舍 1 已论证） |
| **B. 纯租约竞争** | Worker 通过 ZK/etcd lease 竞争任务，先到先得 | 任务发布方 | 各自竞争 | ⚠️ 简单但粗糙，无法做加权均衡和确定性认领，缺少防脑裂 |
| **C. 一致性哈希** | target 哈希到节点，节点变更时最小迁移 | 维护哈希环 | 按环执行 | ❌ 无法做加权、无法做优雅驱离、迁移时相位不对齐会导致数据断裂 |
| **D. v0.2 方案：声明式 + VRRP 自治** | 平台声明 Zone Manifest（期望态），区内 VRRP 式 slot 归属自治 | 唯一权威（定义权） | 自治执行（归属权） | ✅ 最终选择 |
| **E. K8s Operator 完整复刻** | CRD 定义 ZoneManifest/SlotAssignment，Controller 做 reconcile | 等同 apiserver | 等同 kubelet | ⚠️ 理念相同但实现过重，适合已有 K8s 基础设施的团队 |

**对比维度**：

| 维度 | A 集中 | B 租约 | C 哈希 | D v0.2 | E K8s |
|------|--------|--------|--------|--------|-------|
| 平台复杂度 | 高 | 低 | 低 | 低（只声明） | 中 |
| 区内复杂度 | 低 | 低 | 低 | 中 | 高 |
| 加权均衡 | ✅ 全局最优 | ⚠️ 竞争不均 | ❌ 难加权 | ✅ 区内加权 | ✅ |
| 故障接管速度 | 慢（等中心） | 快 | 快 | 快（本地多数派） | 快 |
| 防脑裂 | 依赖中心 HA | 弱 | N/A | 强（epoch + fencing） | 强 |
| 降级自治 | ❌ | ✅ | ✅ | ✅（四级降级） | ✅ |
| 数据连续性 | 中 | 低（无相位对齐） | 低 | 高（相位对齐 + catch-up） | 中 |
| 实现成本 | 中 | 低 | 低 | 中高 | 高 |
| 与诉求匹配 | 低 | 中 | 低 | **最高** | 中（过度工程） |

**结论**：D（v0.2 方案）是诉求匹配度最高的选择。B（纯租约）可作为阶段 1 的简化实现，后续迭代到 D。

### 2.2 任务类型差异化网区分配策略

用户要求区分两类任务的网区分配逻辑：

| 任务类型 | 示例 | 网区分配策略 | 变更频率 | 自动化程度 |
|---------|------|-------------|---------|-----------|
| **普通任务** | 主机采集、数据库采集、中间件采集 | 由网区规划自动分配（按实例 IP 所在网段 → 网区映射）；客户可在创建时选择/覆盖网区 | 低（跟随实例台账） | 高：实例台账变更 → 自动触发 Zone Manifest 更新 |
| **探测任务** | 端口探测、拨测、连通性检查 | **始终由客户显式选择网区**，不做自动推导 | 中（客户按需调整） | 低：客户手动指定，平台不自动推断 |

**在 v0.2 框架中的落地**：

```
TaskSpec {
  task_id,
  task_type: "scrape" | "probe",     // ← 新增：任务类型标识
  selector,
  zone_assignment_policy: "auto" | "manual",  // ← 新增：网区分配策略
    // auto: 按实例 IP 网段自动推导（普通任务默认）
    // manual: 客户必须显式指定网区（探测任务默认）
  zone_override: zone_id | null,     // 客户手动覆盖的网区（manual 模式必填）
  ...
}
```

**处理规则**：
- `task_type=scrape` + `zone_assignment_policy=auto`：控制面展开 selector → 查实例台账 → 按网段映射自动分组到各区 → 生成 Zone Manifest
- `task_type=probe` + `zone_assignment_policy=manual`：控制面展开 selector → 检查每个实例的 `zone_override` → 未指定的标记为 `UNASSIGNED` + 告警 → 按指定网区生成 Zone Manifest
- 混合模式：同一 TaskSpec 内部分实例 auto、部分 manual（按 `zone_override` 是否为空自动判断）

### 2.3 云原生模型对标

v0.2 的"声明式 + 自治执行"与 K8s 模型有结构性相似，显式对标有助于团队理解：

| K8s 概念 | 本平台对应 | 说明 |
|---------|-----------|------|
| Deployment（期望态） | Zone Manifest | 平台声明"这个区应该采什么" |
| kubelet（执行+上报） | Collector + Zone Agent | 执行采集 + 上报状态 |
| Controller reconcile loop | 归属协商 + 再均衡 | 检测 diff → 执行收敛 |
| Leader Election | Zone Coordinator 主/备 | etcd lease 或 RDS 租约选举 |
| Pod Disruption Budget | 驱离容量护栏（§12.3） | 保证最小可用容量 |
| Node taint/toleration | 节点标记（maintenance/quarantine/pin） | 影响调度但不强制驱逐 |
| Rolling Update | 滚动升级（§18.2） | 逐批 drain + 观察期 |
| Readiness Probe | WARMING 状态（§15） | 就绪后才接新 slot |
| Liveness Probe | 三层探测（§9.5） | TCP + 应用级 + 金丝雀 |

**差异点**（不能照搬 K8s 的原因）：
- K8s 的 kubelet 不持有"所有 Pod 的定义"，但本平台要求每个 Collector 持有全区 Manifest（取舍 2）——这是为了零拉取接管
- K8s 的 Controller 是中心化的，本平台的归属裁决是分布式的（VRRP 式）——因为跨区链路不可靠
- K8s 不关心"数据连续性"，但监控平台的核心诉求就是数据不能断

**结论**：理念可对标 K8s（降低团队理解成本），但实现不能照搬（监控场景的特殊约束）。

## 四、分阶段实施 Plan

基于 v0.2 §21 的演进路线，细化为可执行的阶段计划，补充任务类型区分和方案迭代路径。

### Phase 0 · 决策收敛（1~2 周）

**目标**：在动手之前拍板所有 P0 问题

| 交付物 | 说明 |
|--------|------|
| 跨区连通模型确认 | M2+M3 混合 or 其他选择 |
| 网区规划初稿 | 网区数量、单区规模、节点数 |
| 存储选型确认 | etcd / ZK / 自研 Coordinator |
| 任务类型清单 | scrape + probe，是否还有其他 |
| 中心长期存储决策 | 做 or 不做 |

### Phase 1 · 骨架与正确性（6~8 周）

**目标**：跑通"平台→区→Worker"基本链路，单节点故障可接管

| 模块 | 工作内容 | 对应 v0.2 章节 | 周数 |
|------|---------|---------------|------|
| **中心控制面** | 实例台账、网段映射、TaskSpec/RuleSpec 版本化、Zone Manifest 生成 | §4、§5 | 2 |
| **任务类型区分** | TaskSpec 增加 task_type + zone_assignment_policy，普通任务自动推导网区，探测任务客户指定 | §4.4（补充） | 1 |
| **跨区通道** | M2 接口自检（digest 短路 + delta 增量） | §6.3 | 1 |
| **本地快照** | 三类快照（Manifest / 归属视图 / 自身状态）+ 原子写入 + hash 校验 | §7 | 1 |
| **归属与 token** | 固定加权 slot + 复合 token fencing + 归属注册表（含历史） | §5.3、§10.3、§11 | 1.5 |
| **节点状态机** | REGISTER → WARMING → HEALTHY → SUSPECT → EXPIRED → FENCED + DRAINING/OFFLINE/QUARANTINED | §15 | 1 |
| **基础查询路由** | 查询网关 + Zone Query Proxy 基础路由 | §17 | 0.5 |

**验收标准**：
- `kill -9` 单节点，≤ 20s 完成接管
- 被 kill 节点复活不产生双主
- 中心控制面停机 30min，各区采集照常（L1 降级）
- 时点归属查询可答
- 普通任务按网段自动分配，探测任务需客户指定网区

### Phase 2 · VRRP 互探与自治（5~7 周）

**目标**：区内完全自治，中心不可用时仍能故障接管

| 模块 | 工作内容 | 对应 v0.2 章节 | 周数 |
|------|---------|---------------|------|
| **peer 互探** | mesh/部分 mesh 拓扑 + 三层探测（TCP + 应用级 + 金丝雀） | §9.2~§9.5 | 2 |
| **观测矩阵** | 双向上报 + 交叉验证 + probe_untrusted 识别 | §9.4 | 1 |
| **多数派投票** | quorum 判定 + 确定性 score 认领 + skew 让位 | §10.1~§10.2 | 1.5 |
| **四级降级** | L0→L1→L2→L3 完整实现，重点打通 L3 纯分布式自治 | §3.2 | 1 |
| **驱离与隔离** | drain/quarantine 流程 + 审批审计 + 标记 TTL | §12 | 1 |
| **自监控** | 关键指标接入（旧 token 次数、LKG 节点数、UNOWNED 数、probe_untrusted 数） | §19 | 0.5 |

**验收标准**：
- Coordinator 主备同时停机，区内仍能完成故障接管（L3）
- 模拟单向网络故障不引发误接管
- 模拟节点谎报"其他人都挂了"不引发接管风暴
- 滚动升级全程无 UNOWNED slot

### Phase 3 · 连续性与优化（4~6 周）

**目标**：数据连续性最大化 + 智能均衡

**验收标准**：
- 进程崩溃场景实测空洞 ≤ 1 个抓取周期，catch-up 成功率 ≥ 99%
- 优雅驱离实测空洞 ≈ 0
- 扩缩容后 30min 内负载偏差收敛到 ≤ 8%

## 五、方案迭代路径（从简到繁）

如果团队希望渐进式引入复杂度，可以按以下路径迭代调度模型：

```
阶段 1 简化版                阶段 2 完整版                阶段 3 优化版
─────────────              ─────────────              ─────────────
纯租约竞争（方案B）    →    加权 slot + VRRP 自治    →    负载感知动态均衡
                           （方案D = v0.2）
· 先到先得              · 加权确定性认领            · 运行时权重调整
· 无相位对齐            · 相位对齐                  · 三重抑制再均衡
· 基础心跳              · 三层探测                  · simulate 预演
· 中心下发即生效         · 四级降级自治              · 动态再均衡
```

**阶段 1 简化版的具体形态**：
- 平台下发 Zone Manifest 到区
- Worker 通过 etcd/ZK lease 竞争 slot（先到先得，按权重设置不同续约频率）
- 心跳用协调层 session（不要求 peer 直连）
- 故障时等 lease 过期 → 其他 Worker 竞争认领
- 不做相位对齐（接受 1 个 interval 的空洞）

**何时升级到完整版**：
- 当 2 节点区需要自动接管时（纯租约无法防脑裂）
- 当数据连续性要求高于 1 个 interval 时
- 当中心不可用仍需区内自治时

## 六、v0.2 文档中发现的潜在改进点

在审视过程中发现的几个可以进一步优化的点：

### 6.1 广告报文的带宽预算缺失

§9.3 定义了 Advertisement 结构，但未给出带宽预算计算。建议补充：
- 全连接 mesh（N=12）× 5s 周期 × 报文大小（~500B）= 12×11×(1/5)×500 ≈ 13.2 KB/s，可忽略
- 部分 mesh（N=50, K=5）× 5s = 50×5×(1/5)×500 ≈ 25 KB/s，仍可忽略
- 结论：带宽不是瓶颈，但应在文档中显式论证

### 6.2 Zone Manifest 变更的灰度策略

§5.2 提到 Manifest 必须"原子生效"，但未讨论灰度。当 Manifest 变更涉及大量 slot 时（如新增 1000 个 target），全区同时应用可能造成瞬时负载飙升。建议：
- Manifest 变更应分批应用（按 slot 批次）
- 或：新 Manifest 先下发到 WARMING 节点验证，再全区推广

### 6.3 多任务类型共存时的 slot 共享策略

当 scrape 任务和 probe 任务共存于同一网区时：
- 是否共享同一组 slot？还是各自独立 slot 池？
- v0.2 §16.2 提到 rc 与 collector "共享同一套网区调度域框架，但独立分组"——这暗示 slot 池独立
- 建议显式确认：scrape slot 和 probe slot 是否独立管理
